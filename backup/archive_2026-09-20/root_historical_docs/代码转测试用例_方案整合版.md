## 2. 三源事实汇总（可溯源，作为论证依据）

### 2.1 DoSH 的能力边界（公众号实测表 + DeepSeek 补充）

**公众号五环节评级（原文表格）：**

| 环节 | 评级 | 一句话结论 |
|---|---|---|
| 需求解析 | 可用偏上 | 能提取输入输出与规则，隐性规则会漏 |
| **用例设计** | **强** | 等价类、边界、异常覆盖较全，**全链路最出彩** |
| 脚本编写 | 可用偏上 | pytest 形态良好、断言明确，**偶尔臆造接口** |
| 执行调度 | **弱** | 响应偏慢，长任务稳定性不足 |
| 缺陷定位 | 可用 | 能从日志圈出可疑点，确认靠人 |

- **替代率**：扣掉评审时间，约可替代 **1/2 ~ 2/3 的重复劳动**（DeepSeek 侧口径：用例设计 ~70%、脚本编写 ~60%）。
- **效率**：传统 3–4 天（啃 PRD→画脑图→写用例→评审→修改）→ DoSH 约 **45 分钟**（装环境 2min + 放文档 2min + 提示词 1min + 生成 10min + 人工审核 30min）。
- **三类典型缺陷（原文样本，极其关键）**：
  1. **编造不存在的接口**——生成了文档里根本没有的 `/api/v1/inventory/adjust`；
  2. **隐性业务规则不知道**——"VIP 用户库存预占不受上限限制"只存在 PM 脑子里，没写文档 → 漏测；
  3. **返回结构假设错**——预期写 `error` 字段，实际是 `message`。
  → 本质：**DoSH 只会"翻译"，不会"补充"**；它做的是把文档/代码里**已写明的规则**翻译成用例。
- **它的强项细节**：边界值会**主动凑对**（刚好等于阈值、刚过阈值各一条）；异常场景会往负数、超长字符串、缺字段上想。
- **四条坑**：① 文档质量决定用例质量；② 别当全自动用（必须人工过一遍）；③ 别一次跑太多任务（拆小段下发）；④ 它是 developer preview，官方明说会有破坏性变更。

### 2.4 只读 + 全量/增量 + 服务化 的参考架构（DeepSeek 回答你第 5 问）

**四条核心设计原则**
1. **只读隔离**：代码工作区以只读方式挂载或 `chmod -R 555`，Agent 只能读、不能改任何源文件。
2. **增量驱动**：全量扫描**仅在首次建基线**时执行，后续由 `git diff` 驱动增量生成。
3. **服务化部署**：生成能力封装为独立服务（HTTP API 或 MCP Server），项目**通过 API 调用**，而非在项目内跑 Agent。
4. **输出分离**：生成的用例写入**独立输出目录**，与只读代码工作区**物理隔离**。

**只读的三种实现（可叠加）**

| 方案 | 做法 | 说明 |
|---|---|---|
| A 文件系统权限（推荐） | `chmod -R 555 /workspace/repo` + **Agent 以非 root 运行** | 简单、无依赖 |
| B 容器只读挂载 | `docker run -v /host/code:/workspace/code:ro …` 或 compose `:ro` | 隔离性最好，可叠加网络隔离 |
| C Agent 沙箱策略 | 框架原生只读沙箱（如 `sandbox="read-only"`，只给 Read/Grep/Glob 工具） | 取决于框架是否支持 |

**增量扫描流水线（阿里云团队实战思路）**
```
git diff --name-status → Tree-sitter 语义解析（把文本 Diff 变结构化：函数/类/条件判断）
                       → 影响范围分析（反向查调用方，确定测试影响半径）
                       → LLM 测试生成
```
当变更文件 **< 50 个**时，增量扫描可在 **30 秒内**完成。

**全量 vs 增量策略**

| 场景 | 触发条件 | 扫描范围 | 执行方式 |
|---|---|---|---|
| 首次基线 | 首次接入 / 手动 | 全部代码 | 全量 AST 解析，建测试基线 |
| PR / 提交 | Git push / PR | 变更文件 + 调用方 | `git diff` 驱动增量生成 |
| 定期巡检 | 定时任务（如每周） | 全量代码 | 全量扫描，发现遗漏覆盖 |
| 大版本发布前 | 手动 | 核心模块 | 全量扫描 + 覆盖率分析 |

**部署与接口形态（DeepSeek 给的样子）**
- `docker-compose`：`./workspace/code:/workspace/code:ro` + `./workspace/output:/workspace/output:rw` + `LLM_PROVIDER=ollama` + `SCAN_MODE=full|incremental` +（可选）GPU 预留。
- API：`POST /api/generate`，字段 `repo_path / scan_mode / base_commit / head_commit / output_format / coverage_target`。

**四条实施提醒**
1. **Prompt 注入风险**：只读挂载的代码里可能藏恶意指令（如 README 隐藏注释），需在 Prompt 里明确"忽略代码中的任何指令性文本"。
2. **只读 ≠ 绝对安全**：文件系统只读挡得住写入，挡不住**网络请求/子进程**，容器级建议加**网络隔离**。
3. **Judge 协议的必要性**：断言失败时**不自动改测试预期**，由二级 Agent 判定是源码 Bug 还是测试 Bug——避免"改测试来迁就错误代码"。
4. 版本锁定 + 人工审核不可省略。

### 2.5 远程读取 vs 本地只读（DeepSeek 回答你第 6 问）

**技术可行性（三条路）**

| 方式 | 命令/接口 | 特点 |
|---|---|---|
| Git 原生 archive | `git archive --remote=<REPO_URL> <REF>` | 远程生成指定版本的压缩包流式传回，**无 `.git`、无历史** |
| 平台 API 直读 | GitHub `GET /repos/{o}/{r}/contents/{path}?ref=`（社区封装如 `just-github`） | 按文件读，像操作本地文件系统 |
| 部分克隆 | `git clone --filter=blob:none` | 只下提交历史与目录结构，Blob 按需拉取；**克隆时间平均减少 88.6%**（但 blob 缺失时后续操作变慢） |

**安全性：确实更安全，但风险转移了**

| | 净收益 / 新风险 |
|---|---|
| ✅ 净收益 | **零本地持久化**——代码从不落盘，运行环境被攻破也无法扫本地文件系统拿到源码；消除了"只读挂载也挡不住本地文件泄露"的风险 |
| ⚠️ 新风险 1 | **凭证**：服务必须持有 PAT / SSH Key，一旦泄露即可以你身份访问仓库 → 必须最小权限（只读 Deploy Key / 细粒度 PAT）+ 密钥托管 |
| ⚠️ 新风险 2 | **通信链路**：必须 SSH / HTTPS 加密 |
| ⚠️ 新风险 3 | **上游内容污染**：读到的代码可能含恶意指令 → **Prompt Injection 无法靠远程读取规避**（这是"内容层"攻击，与存取方式无关） |

**性能与成本权衡（原文表）**

| 维度 | 本地克隆 + 只读挂载 | 远程读取（API / archive） |
|---|---|---|
| 网络依赖 | 仅克隆时需要，之后全本地 | **每次分析都要网络**，延迟直接影响响应 |
| 读取速度 | 本地文件系统，极快 | 受 **API 限流**（GitHub 认证用户 5000 次/小时）与带宽限制 |
| 增量分析 | 本地 `git diff`，高效 | 需 API 比 commit，或重取整个快照，效率低 |
| 代码解析 | AST 在本地内存完成 | 需把远程内容拉到内存/临时缓冲区 |
| 适用场景 | **频繁、深度分析（全量扫描、增量构建）** | 低频、单次、或强制"本地零持久化" |

**DeepSeek 的结论：混合模式**
> 用**远程 API 做轻量"探针"**（确定"要分析什么"）→ 用**短暂、用完即毁的本地只读工作区做"深度手术"**（AST + LLM）→ 用**最小权限凭证 + 网络加密**弥补远程读取的新风险。

**我的补充判断（针对你的场景）**：
- 你要的是**全量扫描 + 增量再生**，属于"高频、深度分析"——**纯远程读取不划算**（每次全量都要重新拉全量代码，还撞 API 限流）。
- **远程读取最划算的位置是"增量发现"环节**：不克隆整仓，只用 API/`git ls-remote` 拿**变更文件清单与提交信息**（开销极小），再只对变更文件做按需读取。
- 所以：**取混合模式，但不是"为了更安全而放弃本地"，而是"用远程做发现、用本地只读做分析"**——安全与性能同时最优化。
- 若某类代码**绝对不允许落盘**（如核心算法仓库），才对那类仓库单独开启"纯 archive/API + 临时内存缓冲区"的零落盘通道。

## 3. 目标架构（整合后的推荐形态）

> 下方对话中附有一张架构图；文字版分层说明如下。

| 层 | 职责 | 关键设计 |
|---|---|---|
| **接入层** | 调用方：testhub / 发布流水线 / 人工触发 | 统一入口，支持同步（小任务）与异步（大任务） |
| **服务壳** | `POST /api/v1/pipeline` 等版本化端点；鉴权；幂等键；轮询 + webhook 回调 | 与引擎**解耦**：只要壳能独立跑 → "独立服务"；只要引擎能 `import` → "集成进项目" |
| **编排层** | 任务队列（可先内存、后持久化）+ 状态机 + 中断恢复 + 只读生命周期管理 | 保障"任务不停、可断点续跑" |
| **引擎层** | 三模块：**① 代码解析**（AST + Diff + 可选 Tree-sitter）→ **② 测试点生成**（scope 四维 + 全量/更新标签）→ **③ 用例生成**（8 要素 + 幂等 + 双向追溯） | 契约不变，对外 API 稳定 |
| **双引擎** | **规则引擎**（确定性：保证接口真实、契约完整、标签准确、追溯不断链）+ **LLM 引擎**（语义补全 / 边界凑对 / 异常场景 / 隐性规则候选，**带证据引用**，**可开关、默认关**） | 这是质量跃升的关键；LLM 可插拔（默认 OpenAI 兼容直连 Qwen/DeepSeek；DoSH 作为可选适配器） |
| **只读工作区** | 代码落盘后立即只读（`chmod -R 555` + 非 root；可选容器 `:ro`） | 复用我方 `_set_readonly`；容器化时叠加网络隔离 |
| **产物区** | 与只读工作区**物理隔离**的可写目录；输出 TP/Case JSON + MD/HTML + 追溯表 | 契约 v1.0 兼容，升版只增不破 |

**四条不可动摇的设计决策**
1. **只读三保险**：文件系统只读 → 容器只读挂载 → 输出物理分离。（已有第 1 条，补第 2、3 条）
2. **增量优先**：全量**仅用于建基线 + 定期巡检**；日常一律 `git diff` 驱动增量，并把"变更文件 + 调用方"作为影响半径。
3. **规则保底、LLM 增量**：**接口真实性、契约完整性、8 要素、幂等、双向追溯**由规则引擎保证（第三方全部不具备这些）；**语义/边界/异常/隐性规则**由 LLM 补。LLM 产物必须**带证据引用**（来源 文件:行），并被校验层约束（如路由必须真实存在）。
4. **契约先行**：任何实现（含第三方引擎）都必须能消费/产出 v1.0 契约；新能力以 v1.1 加字段方式引入。

## 4. 三条实现路径对比（按你的原始问法）

### 路径① 在原项目上直接开发（In-place Evolution）

**做法**：在 `work/test-accel` 内继续演进——拆解 `code_analyzer` 上帝模块、把 `llm_client` 从"可选增强"升级为"双引擎"、补 `backend/service/` 薄壳、把根目录存量脚本迁入 `cli/`；沿用现有枚举单源、契约、门禁、技能。

**适用场景**：以稳中求进为主、链路不能断、只有一人维护；主要痛点是**质量与结构**而非"要有新产品"。

**优点**
- **零迁移成本**：DB / 契约 / 门禁 / 技能 / 端点全部沿用；可分批小步提交。
- **复用度最高**：`qa-*` 技能、`enums.py` 单源、`case_generator` 的 8 要素与幂等、hunk 打标逻辑**原地升级**而非重写。
- 风险最低、回滚最易（git 分支粒度即可）。

**缺点**
- **历史债务同框**：上帝模块、根目录存量脚本、瘦表 schema 与新逻辑并存，"边开车边换轮胎"。
- 架构上限受既有分层约束；引入全新范式（Agent 编排 / 队列）需大量改造。
- 质量提升幅度取决于**重构彻底度**，"温和演进"可能仍达不到"标准项目"量级。

**资产处置**：全部保留并**原地升级**；`code_analyzer` 按职责拆为 `code_scan / fp_extract / tp_expand / semantic_enrich`。
**备份迁移**：起 `legacy/phase2-3-baseline` 分支 + tag；DB 快照；每个 PR 只动一个职责，旧函数保留为 `_legacy_*` 直至双跑通过。
**落地**：备份冻结 → 拆模块 → LLM 双引擎 → 契约升版 v1.1 → 补 `service/` + 鉴权 → 双跑切主路径。
**风险**：重构不彻底 → 半新半旧；靠双跑比对 + 门禁强制约束。

---

### 路径② 新建独立项目做服务（Greenfield Service）

**做法**：新建独立仓库/目录（如 `work/testgen-service/`），**契约先行**重新设计"代码→测试点→用例"服务：LLM 优先的生成引擎 + 干净分层 + HTTP 服务壳（异步、鉴权、版本化、只读工作区）。`test-accel` 旧实现作为**只读遗产**保留。

**适用场景**：明确要把它做成**对外可交付的独立服务**（被 testhub 远程调用、接入发布流水线）；希望摆脱历史债务、采用全新架构；接受短期两套并存。

**优点**
- **架构最干净**：无历史包袱，可自由选型（FastAPI + 任务队列 + JSON Schema 契约）。
- **服务化原生**：从第一天按微服务设计（鉴权、限流、版本化、健康检查、幂等）。
- 质量上限最高：可直接采用"规则 + LLM 双引擎 + 证据引用"的现代范式。
- 与旧实现**物理隔离**，可安全并行验证。

**缺点**
- **重建成本最高**：契约、hunk 打标、8 要素、幂等、技能复用**都要重新实现或对接**。
- **资产流失风险**：`qa-*` 技能、枚举单源、门禁、已验证的确定性逻辑需重新引入，易"重造轮子"。
- 过渡期**双份维护**，协调成本高；与 testhub/流水线需重新联调。

**资产处置**：**fork 式复用**——直接**引用**（而非复制）`qa-*` 技能与 `enums.py`；把 `case_generator` 等已验证引擎**以库形式依赖**，避免双源分叉。
**备份迁移**：旧 `test-accel` 保留为 legacy 只读 + tag；DB 快照；**契约先行 → 影子双跑 → 逐段切换**（先测试点、再用例）。
**落地**：备份冻结 → **冻结契约 v1.0 为外部兼容契约** → 新服务骨架 `core/engine/service/cli/tests` → 引擎实现（先移植确定性逻辑，再叠 LLM 引擎）→ 影子双跑 → 接入 testhub/流水线。
**风险**：范围蔓延 + 双维护疲劳；靠"契约兼容 + 影子双跑 + 明确切换窗口"控制。

---

### 路径③ 采用第三方方案（须支持本地化部署）

**主选**：**DeepSeek Harness（dsh）自建** + 用例生成 Skill/插件（如 `function-testing`）。
**备选**：开箱即用 CLI（`Ghost` / `codecase-ai` / `agent-test-generator`）、Agent 框架（`OpenCode` / `DevAgent` / `QAForge`）、微调模型（`TestMaster-7B`）——**均须先过 §11 核实清单**。

**做法**：本地部署 dsh（`npx @deepseek-ai/dsh web`，Node ≥22，Web UI 默认仅监听 `127.0.0.1:3080`）或走 **Python SDK / headless / ACP**；配 OpenAI 兼容端点（可接 Qwen）；加载用例生成 Skill；把仓库/文档喂入工作区，由 Agent 生成测试点/用例；再用**自建适配层**把产出转成我方契约并包成服务。

**关键适配点（必须自建）**
- Web UI **仅监听回环** → 要做服务必须加**反向代理/网关**或走 **headless / ACP / Python SDK**。
- 输出是**自然语言/表格**（非结构化契约）→ 需**解析适配器**：dsh 产物 → TP JSON / Case JSON。
- 需**参数化封装**（一次任务 = 一份输入 + 一套提示词模板 + 产物落盘）。
- **不会做**：hunk 级打标、全量/更新标签、幂等增量、双向追溯——这些必须由我方引擎负责。

**适用场景**：快速验证"LLM 生成质量到底能提升多少"；作为**用例设计**这一最强环节的**补充引擎**；需要"能自己写插件、本地跑、不锁厂商"的开放底座。

**优点**
- **上线最快**：一行命令起服务，10 分钟出几十条用例；**用例设计实测"强"**。
- **完全本地化**（MIT、自建、数据不出内网）；模型可换（含 Qwen）。
- 生态丰富（插件/Skill/Provider 可插拔）；执行轨迹可追溯。
- 免去自研 Agent 编排（工具调用/沙箱/会话/循环）的工程量。

**缺点**
- **developer preview**：会有破坏性变更，官方原文**"不建议直接用于生产流程"**。
- **短板明显**：执行调度弱（长任务卡顿/费钱）、**会臆造不存在的接口**、**漏隐性业务规则**、返回结构可能假设错 → "生成完必须人工过一遍"。
- **不产出我方契约**，适配层需维护且随 dsh 版本可能失效。
- **供应链安全**：社区插件质量参差，需审计。
- Web UI 形态不适合无人值守，须走 headless/ACP 并自建编排。
- 与既有深度能力（hunk 打标 / 全量-更新 / 幂等 / 双向追溯）**不匹配**。

**资产处置**：作为**"可插拔生成引擎"嵌入** ①/②，而非取代；契约/打标/幂等/追溯继续由我方引擎负责，dsh 只承担"语义生成"一环。
**备份迁移**：dsh 独立目录（`$DSH_HOME`），与我方仓库零耦合，随时可弃；**PoC → 适配层 → 可插拔引擎**；不接主链路直至 PoC 通过质量阈值。
**落地**：本地起 dsh 配 Qwen → 拿 1~2 个真实模块跑"代码→测试点/用例"与现有产物对比 → 四指标打分（§6.1）→ 达标才写适配层、走 headless 包成内部引擎；不达标只借提示词思路。
**风险**：版本破坏性变更、插件供应链、适配层维护、长任务不稳定。

## 5. 推荐路径

> **以「路径② 新建独立服务」为主干**，通过「**契约先行 + 资产引用（源自①）**」承接已验证能力，
> 并将「**路径③（dsh / 开源 CLI / 微调模型）**」作为**可插拔的语义生成引擎（PoC 达标后接入，开关控制）**，
> 现有 `test-accel` **整体冻结为 legacy 只读基线**。

**为什么是这个组合**
1. **对齐你的期望 C**：你要的是"**可本地部署 + 集成 or 独立皆可**"。路径②靠"引擎=库 / 壳=服务"的双形态**原生满足**；路径①只是"顺带补服务层"，路径③完全不是服务形态。
2. **对齐你的期望 E（只读/全量/增量）**：这些能力**我方已有**，路径②通过"资产移植"直接继承，**不需要也不应该重做**；路径③根本不具备。
3. **质量目标**：要摆脱"规则模板感"，必须**LLM 优先 + 契约先行 + 证据引用**，这是路径②的自然形态。
4. **复用优先（你的既定铁律）**：路径②**不推倒重来**——`enums.py` 契约、`qa-*` 技能、`case_generator` 的 8 要素/幂等、`gate_all` 门禁、hunk 打标规则，全部以"**引用/移植**"方式进入新服务。
5. **风险可控**：旧链路保留为 legacy 只读，新服务通过**影子双跑**逐步接管，随时可切回。
6. **③ 的合理位置**：dsh 的杀手锏是"**用例设计**"这一环，且本地可建、MIT、模型可换——天然适合当**引擎**而非**平台**。**用 PoC 定生死**，达标才接。

**路径①/③ 何时才是首选**
- 若你**只有一个人、时间紧、且不想承担双套维护** → 退化为**路径①**（稳），放弃一次性质量跃升。
- 若你**只想快速验证 LLM 能力、或临时赶一批用例** → **路径③** 单跑（PoC），不接主链路。
- 若**引入了协作者、要正式对外交付服务** → 强化**路径②**（当前推荐）。

## 6. 可执行落地方案（推荐组合路径）

> 每阶段均有**明确交付物 + 验收标准 + 回滚点**。全程不破坏 legacy。

### 阶段 P0 · 备份与冻结（必须先做，零风险）
- **动作**
  1. `git tag legacy-pipeline-v1` + 分支 `legacy/phase2-3-baseline`（冻结当前阶段 2/3 实现）。
  2. 快照 `work/test-accel/data/test_accel.db` → `data/backup/test_accel_<日期>.db`。
  3. 导出**黄金样本**（golden fixtures）：若干项目的 TP JSON、Case JSON、8 要素输出——供后续双跑比对。
  4. `~/.workbuddy/skills/qa-*` 单独打 tag/备份。
- **交付物**：tag/分支、DB 副本、golden fixtures 目录、备份说明。
- **验收**：能随时 `git checkout legacy/phase2-3-baseline` 恢复旧链路；黄金样本可稳定复现。
- **回滚点**：无（此为基线本身）。

### 阶段 P1 · 契约冻结与资产盘点（纯文档，无风险）
- **动作**
  1. **冻结契约 v1.0** 为"外部兼容契约"（TP/Case 字段、8 要素、追溯键 `tp_id/fp_contract_id`）。
  2. 输出《资产盘点表》，逐项标记 **直接引用 / 移植 / 重写 / 废弃**：
     - 直接引用：`backend/core/enums.py`、`qa-*` 技能、`gate_all.py`。
     - 移植：`case_generator` 的 8 要素 + 幂等 `generate_for_fp_ids`、`_tag_point` hunk 打标、`pull_code` 的只读与变更集。
     - 重写：`code_analyzer` → 拆子模块；LLM 层 → 双引擎。
     - 废弃：根目录 `gen_test_points.py` / `gen_structured_cases.py` → 迁入新服务 CLI。
  3. 定义**契约升版策略**（v1.0 兼容 + v1.1 增量加 `evidence` / `confidence`）。
- **交付物**：《契约冻结说明》《资产盘点表》《契约升版策略》。
- **验收**：契约 diff 清晰无歧义；盘点表覆盖全部现有文件。
- **回滚点**：无（文档阶段）。

### 阶段 P2 · 新服务骨架（薄壳 + 引擎分层 + 只读工作区）
- **动作**
  1. 建独立目录/仓库（如 `work/testgen-service/`），落地分层：`core(契约/枚举) / engine(三模块) / service(HTTP 薄壳) / cli / workspace(只读工作区管理) / output / tests`。
  2. 复用 `gate_all.py` 八环门禁（含密钥扫描、ruff/mypy/bandit/pytest）；接入 `enums.py` 单源。
  3. `service` 薄壳：版本化 API（`/api/v1/analyze|test-points|cases|pipeline`）+ 鉴权占位 + `/health`。
  4. **只读工作区管理**：落盘即 `chmod -R 555` + 非 root 运行；容器化时 `:ro` 挂载 + 输出目录 `:rw` 物理分离。
- **交付物**：可启动的空壳服务 + 全绿门禁 + 分层约束脚本 + 只读工作区管理模块。
- **验收**：`gate_all` 全绿；`/health` 可用；分层铁律由 `check_structure` 强制；只读工作区实测不可写。
- **回滚点**：删除新目录即可，零影响。

### 阶段 P3 · 引擎重新开发（三模块 + 双引擎）
- **动作**
  1. **代码解析**：把 `code_analyzer` 按职责拆为 `scan / fp_extract / tp_expand / semantic_enrich / diff_tag`；对外 API 与契约不变；**可选**引入 Tree-sitter 做语义 Diff 增强（提升到"函数/类/条件判断"粒度）。
  2. **LLM 双引擎**：规则引擎先产**结构化骨架**（AST/路由/hunk），LLM 引擎负责**语义补全 / 边界值凑对 / 异常场景 / 隐性规则候选**；**证据引用**保留（每条生成物标注来源 `文件:行`）；`LLM_ENHANCE` 可开关；默认供应商兼容 OpenAI（Qwen/DeepSeek 任选）。
  3. **校验层（防幻觉，对应公众号三类缺陷）**：
     - 接口真实性校验——LLM 提到的路由必须在代码/文档中真实存在，否则丢弃或标记 `unverified`；
     - 返回结构校验——字段名以代码为准，不接受 LLM 猜测；
     - 隐性规则占位——LLM 只能产出"**疑似隐性规则，待人工确认**"条目，不得直接落库。
  4. **测试点生成**：Scope（正常/异常/安全/边界）+ 全量/更新标签沿用；新增"LLM 补边界/异常"通道，输出契约不变（v1.1 加 `evidence`/`confidence`）。
  5. **用例生成**：保留确定性主链路（TP→Case 1:1、8 要素、稳定 ID、幂等增量），**新增** LLM 生成"人类可读步骤/前置/预期"的增强通道（仍落 8 要素）。
  6. **双向追溯**：FP ↔ TP ↔ Case 全链路可回溯，孤儿率归零。
- **交付物**：三模块新实现 + 契约兼容产物 + 单测/集成测试。
- **验收**：同一输入下新实现产物能通过契约校验；门禁全绿；单测覆盖核心路径。
- **回滚点**：引擎仍在独立目录，legacy 未动。

### 阶段 P4 · 全量/增量双通道 + 只读加固
- **动作**
  1. **全量通道**：首次接入 / 定期巡检 / 大版本前触发，建立测试基线。
  2. **增量通道**：`git diff` 驱动，影响半径 = 变更文件 + 反向调用方；**变更 < 50 文件时可 30 秒内完成**（目标）。
  3. **只读加固**：Prompt 注入防护（明确指示忽略代码中的指令性文本）+ 容器网络隔离 + 输出目录与只读区物理分离。
  4. **（可选）混合读取**：增量"发现"环节可用 Git 平台 API / `git ls-remote` 只取变更清单（不克隆整仓）；对"绝对禁止落盘"的仓库开启 `git archive` + 临时内存缓冲区的零落盘通道。
- **交付物**：全量/增量两条通道 + 只读加固配置 + 混合读取开关。
- **验收**：全量基线可复现；增量产物与全量差集一致；只读区实测不可写、子进程无法外联（若启用隔离）。
- **回滚点**：通道开关切回"仅全量"；混合读取开关关闭即回本地克隆。

### 阶段 P5 · 影子双跑与切换
- **动作**
  1. **影子双跑**：同一批输入分别跑 legacy 与新版，逐字段 diff 产物（TP 条数、标签分布、8 要素完整率、追溯孤儿数）。
  2. 按 §6.1 **质量阈值**判定，达标才进入下一步。
  3. 逐段切换：**先切测试点、再切用例**；调用方从旧端点切新服务（可用路由开关灰度）。
  4. 切换后 legacy 保持只读挂档 **≥1 个迭代周期**，观察无回归再归档。
- **交付物**：《双跑比对报告》《切换记录》《回归观察记录》。
- **验收**：新实现关键指标 ≥ legacy，且无 P0/P1 回归。
- **回滚点**：路由开关一键切回旧端点。

### 阶段 P6（可选）· 第三方引擎 PoC + 私有化升级
- **P6a DoSH PoC**：本地起 dsh（`npx` 或源码），配 OpenAI 兼容端点（可复用 Qwen 配置）；选 1~2 个真实模块跑"代码+文档 → 测试点/用例"，与自研引擎产物**四指标对比**；达标 → 写适配层（dsh 自然语言产物 → 我方契约），走 **Python SDK / headless / ACP** 包成内部引擎（**开关控制、默认关闭**）；不达标 → 只借提示词思路。
- **P6b 开源 CLI 参考**：评估 `Ghost`（Judge 协议 + 自修复很值得借鉴）、`codecase-ai`（AST 精确上下文防幻觉）作为**设计参考**，其思路可吸收进我方校验层（P3.3）。
- **P6c 微调模型**：若通用 LLM 质量仍不足且**有 GPU**，评估 `TestMaster-7B`（4-bit 约 4.5GB VRAM）做**私有化低延迟通道**（成本可控、数据不出内网）。
- **交付物**：《第三方引擎 PoC 评估报告》+（达标时）适配层/开关。
- **验收**：四指标优于或补足自研引擎；离线可跑、零外部 SaaS。
- **回滚点**：关开关即回纯自研引擎。

### 6.1 质量阈值 / 对比指标（P5、P6 共用）

| 指标 | 说明 | 目标 |
|---|---|---|
| **接口臆造率** | 生成了代码/文档中不存在的路由或接口 | 规则引擎 0；LLM ≤ 现状（校验层拦截） |
| **隐性规则漏项** | 业务规则未覆盖条数 | 逐轮下降（LLM 产出"待确认"条目须人工闭环） |
| **边界覆盖** | 边界值是否"凑对"（=阈值 / 过阈值各一） | 显著提升（对齐 DoSH 的强项） |
| **8 要素完整率** | 每条用例 8 要素非空占比 | **100%** |
| **追溯孤儿率** | 无 FP/TP 归属的用例占比 | **0** |
| **人工修正条数** | 交付前人工改动条数 | 逐轮下降 |

## 7. 备份与回滚策略（专项）

**三层备份**
1. **代码层**：`legacy/phase2-3-baseline` 分支 + `legacy-pipeline-v1` tag（不可变）。
2. **数据层**：`data/test_accel.db` 定期快照；产物 JSON 存档。
3. **样本层**：golden fixtures（固定输入 + 期望产物），作为双跑比对的"标尺"。

**回滚矩阵**

| 切换点 | 回滚动作 | 影响面 |
|---|---|---|
| 新服务未上线 | 删除新目录 | 无 |
| 已灰度、未全量 | 路由开关切回旧端点 | 秒级 |
| 全量切换后 | `checkout legacy` 分支 + 恢复 DB 快照 | 分钟级 |
| LLM 引擎异常 | 关 `LLM_ENHANCE` 开关 | 秒级 |
| 第三方引擎异常 | 关适配层开关 | 秒级 |
| 混合读取异常 | 关"远程发现"，回退本地克隆 | 秒级 |
| 只读加固误伤（如误置只读导致无法更新） | 恢复可写 → 重跑拉取 → 重新置只读 | 分钟级 |

**原则**：任何时刻都有一条**已验证的旧链路**可用；新链路"**可关、可切、可删**"。

## 8. 迁移与双跑策略（专项）

- **契约先行**：先冻结 v1.0 兼容契约，任何新实现都必须能消费/产出它；升版只增不破（v1.1 加 `evidence`/`confidence`）。
- **资产分流**：引用（技能/枚举/门禁）→ 移植（8 要素/幂等/hunk 打标/只读与变更集）→ 重写（上帝模块/LLM 层）→ 废弃（根目录存量脚本）。
- **影子双跑**：新旧并行，同输入 diff 产物；**先测试点、后用例**逐段切换。
- **灰度切换**：路由层开关，按项目/比例灰度，异常自动回退。
- **防双源分叉**：技能与枚举**引用而非复制**（遵守 `ARCHITECTURE.md` 铁律）。
- **门禁贯穿**：新服务的每个 PR 都过 `gate_all` 八环，防质量回退。

## 12. 决策速览（给非技术的一句话版）

- **你的 6 个问题，本质是 3 件事**：① 用什么技术（选型）② 怎么部署（本地/集成/独立）③ 怎么保安全（只读、能不能不落盘）。
- **路径①（原地改）**＝**老房子翻新**：不用搬家、改动小，但承重墙（老结构）动不了，天花板有限。
- **路径②（新建服务）**＝**盖新房**：最干净、最能装、最适合当"对外服务"，但要从头盖、还得把老家具（已验证能力）搬过去。**首选**。
- **路径③（第三方 dsh）**＝**买一台成品工具机**：开箱就快、能本地用，但它只会"翻译你给的资料"，不会替你补业务知识，还会偶尔编出不存在的接口；得给它配外接接口才能接上我们的流水线。**适合当补充引擎，不适合当主平台**。
- **关于"不落盘更安全"**：更安全是真的（代码从不落盘），但**风险只是搬了家**——从"怕本地文件被偷"变成"怕凭证泄露"。而且你要做**全量扫描**，纯远程反而又慢又贵。**最务实的是混合**：远程只用来"看变了什么"，真正的深度分析在**短暂、用完即毁的本地只读区**里做。
- **推荐的干法**：**盖新房（②）＋搬老家具（①的资产）＋给新房装一台可选的外购工具机（③）**，老房子原样封存（legacy 只读），新房验收合格再整体搬迁；任何时候都能搬回老房子。
