## 五、整体验证结论

1. **阶段1 逻辑正确**：在「有效 git 仓库」上，`pull_code.py` 能正确计算 `base..target` 变更集、将工作树切到 target、产出结构合规的 `.pull_result.json`，且离线/异常时优雅降级、退出码恒 0（V1 全 PASS）。
2. **阶段2 高质量**：真实代码上生成 263 测试点 / 237 功能点，双向追溯覆盖 100%、孤儿 0、业务域完整恢复、语义 100% 覆盖、去重扫描生效（V2/V3 全 PASS，无回归）。
3. **阶段衔接契约 sound**：阶段1 的 `changed_files` 经 `CHANGED_FILES_JSON` 被阶段2 无 git、无 import 地直接消费，正确驱动「更新」标签（变更文件 → 更新，未变更 → 全量），fixture 与真实代码双重验证通过（V4 全 PASS）。
4. **⚠️ 唯一阻断项（P1）**：生产 `research-agent` 目录**不是独立可用 git 仓库**（其 `.git` 是孤儿目录，git 一律向上解析到父仓库 `testCodeFast`）。这导致：
   - 阶段1 当前**无法对真实 target 正确产出差分**（git 会作用到父仓库；且 `qa-code-pull` 缺少 code_analyzer 已有的 `_git_repo_usable()` 顶层级守卫，会误判该目录为有效仓库）。
   - 因此真实链路现以**安全降级**方式运行：阶段2 走内部 git diff 兜底，因基线 ref 失效得到空变更集 → **全部标「全量」**，未启用「更新」增量回归能力。

> 结论：两阶段各自的**算法与契约均验证通过**，端到端“接通”在逻辑上成立；但**差分能力的真实落地被生产仓库的 git 失效阻断**，必须在投产前修复（见问题 P1）。

## 六、存在的问题（按优先级）

### 🔴 P1（必须）— 生产 target 的 git 失效 + 阶段1 缺顶层级防护
- **现象**：`git -C research-agent rev-parse --show-toplevel` 返回 `…/testCodeFast`；`research-agent/.git` 是孤儿目录（含 logs/objects/refs 但 git 不认其为控制仓库）。
- **风险**：`qa-code-pull` 若对本路径执行 `git diff/checkout`，会操作**父项目仓库**，可能污染 testCodeFast 工作树；且 `is_git_repo()` 因父仓库 `is-inside-work-tree=true` 误判有效。
- **建议**：
  1. 修复 target 为真正独立的 git 仓库（重新 clone 到独立目录，或重建 `.git` 指向自身）；
  2. 给 `pull_code.py` 补 `_git_repo_usable()` 顶层级校验（与 `code_analyzer` 一致：`--show-toplevel` 必须落在 `LOCAL_PATH` 内，否则降级返回空集并报错），**物理阻断误作用父仓库**。

### 🟡 P2（应做）— 基线 ref 失效
- `test-20260906` / `test-20260907` 已不存在（仓库仅 `main`），真实差分集恒为空。
- **建议**：重建基线（在 `main` 上指定两个有效对比提交）或通过 `TP_DIFF_BASE`/`TP_DIFF_TARGET` 显式传入，使「更新」增量回归真正可用。

### 🟡 P3（应做）— 阶段1 产物未实际沉淀
- 本会话 `.pull_result.json` 从未生成（阶段2 一直走内部 git 兜底）。
- **建议**：修复 P1 后正式跑一次 `pull_code.py`，沉淀真实 `.pull_result.json`，让“阶段1→阶段2 文件契约”在真实环境闭环（而非仅 fixture 验证）。
