# 从代码解析到用例生成 · 重新开发方案：三路径对比与可执行建议

> 交付性质：**方案文档，不含任何代码开发**。
> 目标范围：`代码解析` → `测试点生成` → `用例生成` 三段（即 PIPELINE 阶段 2 + 阶段 3）。
> 前提约束：现有功能**先保留备份**；重新开发不得中断现有链路。

**Harness（dsh）权威事实**（据官方文档与实测文章交叉核对）：
- DeepSeek 2026-08-13 开源的 Agent 运行框架，**MIT 协议**，现处 **developer preview**（v0.1.0-rc.x，官方明确"会有破坏性变更"）。
- 核心理念 **"一切皆插件"**（基于 Cordis 内核）；官方定位 **Agent = Model + Harness**（模型是大脑，Harness 是手脚/工具/调度/沙箱/存储）。

- 模型可换：官方 DeepSeek，或**任意 OpenAI 兼容端点**（可接 Qwen 等，契合我方现有 `QWEN_*` 配置）。
- 社区已有 `function-testing` 等"用例生成"Skill 可直接装。

### 0.3 结论性判断（为什么"质量差一个层级"）

1. **生成逻辑以 AST 确定性规则为主，LLM 只是"可选增强"**——上下文理解、业务语义、隐性规则推断能力天然受限，产出偏"机械模板"。
2. **上帝模块承载过多职责**（1583 行），规则耦合、迭代成本高，质量提升被结构拖累。
3. **契约与产物分散**：8 要素未完整落库、根目录存量脚本游离于门禁之外。
4. **无服务化外壳**：`backend/service/` 缺失、无鉴权/调度，难以被 testhub 或流水线稳定调用。
5. 因此"重新开发"的**真实目标**不是重写一遍同样的 AST 规则，而是**把生成范式从"规则驱动"升级为"规则+LLM 双引擎、契约先行、可服务化"**。

## 1. 目标、范围与约束

**目标**
- 重新开发 `代码解析 / 测试点生成 / 用例生成` 三段，显著提升生成质量（业务语义、边界/异常覆盖、隐性规则推断）。
- 产出**结构化、可追溯、可幂等增量**的测试点与用例（保持契约 v1.0 兼容或有序升版）。
- 具备**服务化**条件（薄壳 + 引擎分层、可鉴权、可被远程/流水线调用）。

**范围内**：阶段 2 + 阶段 3（含二者间的契约与追溯链）。
**范围外（本期不动）**：阶段 4 执行、阶段 5 监控、阶段 6 报告、前端 UI；如需联动，仅保证契约不破。

**硬约束**
- 现有功能**先备份**，新实现在切换前**不破坏**既有链路。
- **本地化部署**（不得依赖不可自建的外部 SaaS）。
- 复用优先：已有技能/枚举/门禁/契约应复用，不重复造轮子。
- 遵守 `ARCHITECTURE.md` 分层铁律与 `gate_all.py` 门禁。

## 2. 三条路径详解

### 路径① 在原项目上直接开发（In-place Evolution）

**做法**：在 `work/test-accel` 内继续演进。拆解 `code_analyzer` 上帝模块、强化 `llm_client` 为"双引擎"、补 `backend/service/` 薄壳、把根目录存量脚本迁入 `cli/`；沿用现有枚举单源、契约、门禁、技能。

**适用场景**
- 以"稳中求进"为主，链路不能断，团队只有你一人。
- 主要痛点是**质量与结构**，而非"要一个全新产品"。
- 需要前后端/执行/报告全链路保持兼容。

**优点**
- **零迁移成本**：DB、契约、门禁、技能、端点全部沿用；改动可分批小步提交。
- 复用度最高：`qa-*` 技能、`enums.py` 单源、`case_generator` 的确定性能力、8 要素派生规则、hunk 打标逻辑都可**原地升级**而非重写。
- 风险最低、回滚最易（git 分支粒度即可）。
- 与已规划的"独立服务"方向不冲突——本路径本身就在补 `service/` 层。

**缺点**
- **历史债务同框**：上帝模块、根目录存量脚本、瘦表 schema 会与新逻辑并存，重构期间"边开车边换轮胎"。
- 架构上限受既有分层约束；若想引入全新范式（如 Agent 编排/队列），需大量改造而非自由设计。
- 质量提升幅度取决于**重构彻底度**，"温和演进"可能仍达不到"标准项目"量级。

**对现有资产的处置**：全部保留并**原地升级**；`code_analyzer` 按职责拆分为 `code_scan / fp_extract / tp_expand / semantic_enrich` 等子模块。

**迁移与备份策略**
- 备份：起 `legacy/phase2-3-baseline` 分支 + `git tag`，整库快照 `data/test_accel.db`。
- 迁移：**增量改造**，每个 PR 只动一个职责；旧函数保留为 `_legacy_*` 直至新路径通过双跑比对。
- 回滚：切回 `legacy` 分支即可。

**落地步骤**
1. 备份与冻结：tag + 分支 + DB 副本 + 产物黄金样本（golden fixtures）。
2. 拆分上帝模块：`code_analyzer` → 4 个子模块，保持对外 API 不变（门禁守护）。
3. LLM 双引擎：`llm_client` 抽出 `analyze_with_llm()`，规则先跑、LLM 补语义/边界/隐性规则，**可选开关**。
4. 测试点/用例契约升版（v1.0 → v1.1，向后兼容）。
5. 补 `backend/service/` 薄壳 + 鉴权 + 版本化 API。
6. 双跑比对 → 灰度切主路径。

**风险**：重构不彻底会"半新半旧"；需以双跑比对 + 门禁强制约束。

### 路径② 新建独立项目做服务（Greenfield Service）

**做法**：新建独立仓库/目录（如 `work/testgen-service/`），**契约先行**重新设计"代码→测试点→用例"服务：LLM 优先的生成引擎 + 干净分层 + HTTP 服务壳（异步、鉴权、版本化）。test-accel 旧实现作为**只读遗产**保留。

**适用场景**
- 明确要把它做成**对外可交付的独立服务**（被 testhub 远程调用、接入发布流水线）。
- 希望摆脱历史债务、采用全新架构（LLM 优先 / Agent 编排 / 队列）。
- 有精力做"一次到位的正规工程"，接受短期两套并存。

**优点**
- **架构最干净**：无历史包袱，可自由选型（如 FastAPI + 任务队列 + 契约 JSON Schema）。
- **服务化原生**：从第一天就按微服务设计（鉴权、限流、版本化、健康检查、幂等）。
- 质量上限最高：可直接采用"规则 + LLM 双引擎 + 证据引用"的现代范式。
- 与旧实现物理隔离，**互不影响**，可安全并行验证。

**缺点**
- **重建成本最高**：契约、hunk 打标、8 要素、幂等增量、技能复用等**都要重新实现或对接**。
- **资产流失风险**：`qa-*` 技能、枚举单源、门禁、已验证的确定性逻辑需重新引入，易"重造轮子"。
- 过渡期**双份维护**（旧链路仍需可用），协调成本高。
- 与 testhub/流水线的集成需重新联调。

**对现有资产的处置**：**fork 式复用**——直接**引用**（而非复制）`qa-*` 技能与 `enums.py` 契约；把 `case_generator` 等已验证引擎**以库形式依赖**，避免双源分叉。

**迁移与备份策略**
- 备份：旧 `test-accel` 保留为 `legacy` 只读，打 tag；DB 快照。
- 迁移：**契约先行 → 影子双跑 → 逐段切换**（先切测试点、再切用例），旧实现兜底直至新实现稳定。
- 回滚：调用方从"新服务地址"切回"旧端点"即可。

**落地步骤**
1. 备份与冻结（同①）。
2. **冻结契约 v1.0 为"外部兼容契约"**，新服务必须能消费/产出之。
3. 新服务骨架：`core(契约/枚举) / engine(三模块) / service(薄壳)` + 门禁。
4. 引擎实现：优先**移植**已验证的确定性逻辑（hunk/8 要素/幂等），再叠加 LLM 引擎。
5. 影子双跑：同一输入跑新旧两套，diff 产物，趋稳后切换。
6. 接入 testhub / 流水线。

**风险**：范围蔓延 + 双维护疲劳；必须以"契约兼容 + 影子双跑"控制。

### 路径③ 采用第三方方案（Third-party，须支持本地化部署）

**主选：DeepSeek Harness（dsh）自建 + 用例生成 Skill/插件**。
备选同类：任意**可自建的 OpenAI 兼容 LLM + 提示工程/框架**（轻量版），或开源 Agent 框架（如基于 Cordis 生态的插件）。

**做法**：本地部署 dsh（`npx`/源码，Node ≥22，Web UI 回环），配置模型（DeepSeek 或 Qwen 兼容端点），加载用例生成 Skill（如 `function-testing`），把持仓库/文档喂入工作区，由 Agent 生成测试点/用例；再用**自建适配层**把产出转成我方契约，并包成服务。

**关键适配点（必须自建）**
- dsh 的 Web UI **仅监听 `127.0.0.1`**，要做"服务"需加**反向代理/网关**或走 **headless / ACP** 形态。
- dsh 输出是**自然语言/表格**（非我方结构化契约），需**解析适配器** → TP JSON / Case JSON。
- 需要**参数化封装**（一次任务=一份输入+一套提示词模板+产物落盘）。

**适用场景**
- **快速验证/短平快增强**：想先看"LLM 生成质量到底能提升多少"，再决定长期投入。
- 作为**生成引擎的补充**（尤其"用例设计"这一最强环节），而非全链路替换。
- 需要"能自己写插件、能本地跑、不锁定厂商"的开放底座。

**优点**
- **上线最快**：一行命令起服务，10 分钟出几十条用例；用例设计环节质量实测"强"。
- **完全本地化**（MIT、自建、数据不出内网）；模型可换（含 Qwen）。
- 生态丰富（插件/Skill/模型 Provider 均可插拔）；执行轨迹可追溯。
- 免去自研 Agent 编排（工具调用/沙箱/会话/循环）的工程量。

**缺点**
- **developer preview**：会有破坏性变更，**不建议直接用于生产流程**（官方原文）。
- **短板明显**：执行调度弱（长任务卡顿/费钱）、**会臆造不存在的接口**、**漏隐性业务规则**、返回结构可能假设错——"生成完必须人工过一遍"。
- **不产出我方契约**：需要维护适配层，且适配层随 dsh 版本可能失效。
- **供应链安全**：社区插件质量参差，需审计（我方已有 skills-security-check 思路可复用）。
- **自动化程度**：Web UI 形态不适合无人值守，须走 headless/ACP 并自建编排。
- 与既有"hunk 级打标 / 全量-更新标签 / 幂等增量 / 双向追溯"等**深度能力不匹配**（dsh 不做这些）。

**对现有资产的处置**：**作为"可插拔生成引擎"嵌入** ①/②，而非取代；现有契约、打标、幂等、追溯**继续由我方引擎负责**，dsh 只承担"语义生成"的一环。

**迁移与备份策略**
- 备份：dsh 独立目录（`$DSH_HOME`），与我方仓库零耦合，随时可弃。
- 迁移：**PoC → 适配层 → 可插拔引擎**；不接主链路，直至 PoC 通过质量阈值。
- 回滚：关掉开关即回到纯规则引擎，零残留。

**落地步骤**
1. PoC：本地起 dsh + 配 Qwen 兼容端点；拿 1~2 个真实模块跑"代码→测试点/用例"，与现有产物对比。
2. 质量评估：用"接口臆造率 / 隐性规则漏项 / 边界覆盖 / 人工修正条数"四指标打分。
3. 若达标 → 写适配层（dsh 产物 → 我方 TP/Case 契约），包成 headless 服务。
4. 若仅小幅优于现状 → 仅作"提示词参考"，不引入运行时依赖。

**风险**：版本破坏性变更、插件供应链、适配层维护、长任务不稳定。

| 生产可用成熟度 | **★★★** | ★★（需建设） | ★（developer preview，官方禁生产） |
| 本地化/合规 | **★★★** | **★★★** | **★★★**（可完全自建） |
| 深度能力匹配<br>（hunk 打标/全量-更新/幂等/双向追溯） | **★★★** | ★★（需重建） | ★（不具备） |

**一句话结论**
- 要**质量跃升 + 长期服务** → ② 最强，但成本最高。
- 要**低风险稳进 + 与全链路兼容** → ① 最稳。
- 要**快速见效 + 开放底座** → ③ 最快，但不能当主链路，只适合做"引擎/参考"。

## 4. 推荐路径：② 为主干 + ① 资产迁移 + ③ 作可插拔引擎

**推荐组合路径（分主次，非折中含糊）**：

> **以「路径② 新建独立服务」为主干**，通过「**契约先行 + 资产引用（源自①）**」承接已验证能力，
> 并将「**路径③ dsh**」作为**可插拔的语义生成引擎（PoC 验证后接入，开关控制）**，
> 现有 test-accel **整体冻结为 legacy 只读基线**。

**为什么是这个组合**
1. **方向一致性**：你已明确 test-accel 的定位是**独立服务**（被 testhub 调用 + 接入发布流水线）。路径②原生满足；路径①只是"顺带补服务层"，路径③完全不是服务形态。
2. **质量目标**：要摆脱"规则模板感"，必须**LLM 优先 + 契约先行**，这是路径②的自然形态；路径①受历史结构牵制，路径③不产出我方契约。
3. **复用优先（你的既定铁律）**：路径②**不推倒重来**——`enums.py` 契约、`qa-*` 技能、`case_generator` 的 8 要素/幂等逻辑、`gate_all` 门禁、hunk 打标规则，全部**以"引用/移植"方式进入新服务**，不重复造轮子。
4. **风险可控**：旧链路整体保留为 legacy 只读，新服务通过**影子双跑**逐步接管，随时可切回。
5. **③ 的合理位置**：dsh 的杀手锏是"用例设计"这一环，且**本地可建、MIT、模型可换**——天然适合当**引擎**而非**平台**。用 PoC 定生死，达标才接，不达标只借提示词思路。

**路径①/③ 何时才是首选**
- 若你**只有一个人、时间紧、且不想承担双套维护** → 退化为**路径①**（稳），放弃一次性质量跃升。
- 若你**只想快速验证 LLM 能力、或临时赶一批用例** → **路径③** 单跑（PoC），不接主链路。
- 若**引入了协作者、要正式对外交付服务** → 强化**路径②**（当前推荐）。

## 5. 可执行落地方案（推荐组合路径）

> 每阶段均有**明确交付物 + 验收标准 + 回滚点**。全程不破坏 legacy。

### 阶段 P0 · 备份与冻结（必须先做）
- **动作**
  1. `git tag legacy-pipeline-v1` + 分支 `legacy/phase2-3-baseline`（冻结当前阶段 2/3 实现）。
  2. 快照 `work/test-accel/data/test_accel.db` → `data/backup/test_accel_<日期>.db`。
  3. 把现有产物导出为**黄金样本**（golden fixtures）：若干项目的 TP JSON、Case JSON、8 要素输出——供后续双跑比对。
  4. `~/.workbuddy/skills/qa-*` 单独打 tag/备份（技能是独立版本）。
- **交付物**：tag/分支、DB 副本、golden fixtures 目录、备份说明。
- **验收**：能随时 `git checkout legacy/phase2-3-baseline` 恢复旧链路；黄金样本可稳定复现。
- **回滚点**：无（此为基线本身）。

### 阶段 P1 · 契约冻结与资产盘点
- **动作**
  1. **冻结契约 v1.0** 为"外部兼容契约"（TP/Case 字段、8 要素、追溯键 `tp_id/fp_contract_id`）。
  2. 输出《资产盘点表》：标记每项资产为 **直接引用 / 移植 / 重写 / 废弃**。
     - 直接引用：`backend/core/enums.py`、`qa-*` 技能、`gate_all.py` 门禁。
     - 移植：`case_generator` 的 8 要素派生 + 幂等 `generate_for_fp_ids`、`_tag_point` hunk 打标。
     - 重写：`code_analyzer` 上帝模块 → 拆分子模块；LLM 层 → 双引擎。
     - 废弃：根目录存量脚本（`gen_test_points.py` / `gen_structured_cases.py`）→ 迁入新服务 CLI。
  3. 定义**新服务契约升版策略**（v1.0 兼容 + v1.1 增量）。
- **交付物**：《契约冻结说明》《资产盘点表》《契约升版策略》。
- **验收**：契约 diff 清晰、无歧义；盘点表覆盖全部现有文件。
- **回滚点**：纯文档阶段，无风险。

### 阶段 P2 · 新服务骨架（薄壳 + 引擎分层）
- **动作**
  1. 建独立目录/仓库（如 `work/testgen-service/`），落地分层：`core(契约/枚举) / engine(三模块) / service(HTTP 薄壳) / cli / tests`。
  2. 复用 `gate_all.py` 八环门禁（含密钥扫描、ruff/mypy/bandit/pytest）；接入 `enums.py` 单源。
  3. `service` 薄壳：版本化 API（`/api/v1/analyze|test-points|cases`）+ 鉴权占位 + 健康检查（为服务化铺路）。
- **交付物**：可启动的空壳服务 + 全绿门禁 + 分层约束脚本。
- **验收**：`gate_all` 全绿；`/health` 可用；分层铁律由 `check_structure` 强制。
- **回滚点**：删除新目录即可，零影响。

### 阶段 P3 · 引擎重新开发（三模块）
- **动作**
  1. **代码解析**：把 `code_analyzer` 1583 行按职责拆为 `scan / fp_extract / tp_expand / semantic_enrich / diff_tag`；对外 API 与契约不变。
  2. **LLM 双引擎**：规则引擎先产**结构化骨架**（AST/路由/hunk），LLM 引擎负责**语义补全 / 边界值凑对 / 异常场景 / 隐性规则候选**；**证据引用**保留（每条生成物标注来源文件:行）；`LLM_ENHANCE` 可开关；默认供应商兼容 OpenAI（Qwen/DeepSeek 任选）。
  3. **测试点生成**：Scope（正常/异常/安全/边界）+ 全量/更新标签沿用；新增"LLM 补边界/异常"通道，输出契约不变（v1.1 可加 `evidence`/`confidence` 字段，向后兼容）。
  4. **用例生成**：保留确定性主链路（TP→Case 1:1、8 要素、稳定 ID、幂等增量），**新增** LLM 生成"人类可读步骤/前置/预期"的增强通道（仍落到 8 要素）。
  5. **双向追溯**：FP ↔ TP ↔ Case 全链路可回溯，孤儿率归零（沿用现有 traceability 思路）。
- **交付物**：三模块新实现 + 契约兼容产物 + 单测/集成测试。
- **验收**：对**同一输入**，新实现产物能通过契约校验；门禁全绿；单测覆盖核心路径。
- **回滚点**：引擎仍在独立目录，legacy 未动。

### 阶段 P4 · 影子双跑与切换
- **动作**
  1. **影子双跑**：同一批输入分别跑 legacy 与新版，逐字段 diff 产物（TP 条数、标签分布、8 要素完整率、追溯孤儿数）。
  2. 定义**质量阈值**（见 §5.1），达标才进入下一步。
  3. 逐段切换：**先切测试点、再切用例**；调用方从旧端点切新服务（可用路由开关灰度）。
  4. 切换后 legacy 保持只读挂档 ≥1 个迭代周期，观察无回归再归档。
- **交付物**：《双跑比对报告》《切换记录》《回归观察记录》。
- **验收**：新实现关键指标≥legacy，且无 P0/P1 回归。
- **回滚点**：路由开关一键切回旧端点。

### 阶段 P5（可选）· dsh 作为可插拔引擎 PoC
- **动作**
  1. 本地起 dsh（Node ≥22，`npx @deepseek-ai/dsh web` 或源码构建），配 OpenAI 兼容端点（可复用 Qwen 配置）。
  2. 选 1~2 个真实模块，走"代码+文档 → 测试点/用例"，与我方引擎产物**四指标对比**（§5.1）。
  3. 达标 → 写**适配层**（dsh 自然语言产物 → 我方 TP/Case 契约），走 `headless`/ACP 包成内部引擎；不达标 → 只借提示词思路，不引入运行时依赖。
  4. 全程**开关控制、默认关闭**，供应链安全按 skills-security-check 审计插件。
- **交付物**：《dsh PoC 评估报告》+（达标时）适配层 + 开关。
- **验收**：四指标优于或补足我方引擎；离线可跑、零外部 SaaS。
- **回滚点**：关开关即回纯自研引擎。

### 5.1 质量阈值 / 对比指标（P4、P5 共用）
| 指标 | 说明 | 目标 |
|---|---|---|
| 接口臆造率 | 生成了代码中不存在的路由/接口 | 0（规则引擎）/ 尽量低（LLM） |
| 隐性规则漏项 | 业务规则未覆盖条数 | 逐轮下降 |
| 边界覆盖 | 边界值是否"凑对"（=阈值/过阈值各一） | 显著提升 |
| 8 要素完整率 | 每条用例 8 要素非空占比 | 100% |
| 追溯孤儿率 | 无 FP/TP 归属的用例占比 | 0 |
| 人工修正条数 | 交付前人工改动条数（越低越好） | 逐轮下降 |

## 6. 备份与回滚策略（专项）

**三层备份**
1. **代码层**：`legacy/phase2-3-baseline` 分支 + `legacy-pipeline-v1` tag（不可变）。
2. **数据层**：`data/test_accel.db` 定期快照；产物 JSON 存档。
3. **样本层**：golden fixtures（固定输入+期望产物），作为双跑比对的"标尺"。

**回滚矩阵**
| 切换点 | 回滚动作 | 影响面 |
|---|---|---|
| 新服务未上线 | 删除新目录 | 无 |
| 已灰度、未全量 | 路由开关切回旧端点 | 秒级 |
| 全量切换后 | `checkout legacy` 分支 + 恢复 DB 快照 | 分钟级 |
| dsh 引擎异常 | 关 `LLM_ENGINE` 开关 | 秒级 |

**原则**：任何时刻都有一条**已验证的旧链路**可用；新链路"可关、可切、可删"。

## 7. 迁移与双跑策略（专项）

- **契约先行**：先冻结 v1.0 兼容契约，任何新实现都必须能消费/产出它；升版只增不破（v1.1 加字段）。
- **资产分流**：引用（技能/枚举/门禁）→ 移植（8 要素/幂等/hunk 打标）→ 重写（上帝模块/LLM 层）→ 废弃（根目录存量脚本）。
- **影子双跑**：新旧并行，同输入 diff 产物；**先测试点、后用例**逐段切换。
- **灰度切换**：路由层开关，按项目/比例灰度，异常自动回退。
- **防双源分叉**：技能与枚举**引用而非复制**（遵守 `ARCHITECTURE.md` 铁律 3）。
- **门禁贯穿**：新服务的每个 PR 都过 `gate_all` 八环，防质量回退。

## 9. 决策速览（给非技术的一句话版）

- **路径①（原地改）**＝在**老房子翻新**：不用搬家、改动小、但承重墙（老结构）动不了，天花板有限。
- **路径②（新建服务）**＝**盖新房**：最干净、最能装、最适合当"对外服务"，但要从头盖、还得把老家具（已验证能力）搬过去。**首选**。
- **路径③（第三方 dsh）**＝**买一套成品工具机**：开箱就快、能本地用，但它只会"翻译你给的资料"，不会替你补业务知识，还得给它配外接接口才能接上我们的流水线。**适合当补充引擎，不适合当主平台**。

**推荐的干法**：**盖新房（②）＋搬老家具（①的资产）＋给新房装一台可选的外购工具机（③）**，
老房子原样封存（legacy 只读），新房验收合格再整体搬迁；任何时候都能搬回老房子。
