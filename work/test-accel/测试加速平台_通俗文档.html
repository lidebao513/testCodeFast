测试加速平台 · 通俗使用说明

面向非开发技术人员，用大白话讲清楚：这个平台是干什么的、由哪些部分组成、怎么用、数据怎么流转。

项目名：测试加速平台（test-accel） 所属：testCodeFast 测试工程体系 版本：契约 v1.0
这份文档怎么读？ 全文分 10 章，可以按目录逐章点开阅读。每一章都用日常比喻解释技术概念，遇到"行话"会用 通俗说 小框即时翻译。读完后，你可以基于任意一章的内容，告诉我"想改哪里、想优化哪里"，我再据此动手调整。

第一章　平台是做什么的

简单来说，测试加速平台是一个"帮你自动做软件测试前期工作"的智能助手。它把测试人员最花时间的几件事——读代码、想测试点、写用例、跑一遍看结果——尽可能自动化。

通俗说（打个比方）：假设你要验收一栋新楼。传统做法是你自己拿着图纸一栋栋看、一条条记"这里要检查水电、那里要检查消防"。这个平台就像是：你给它图纸（代码），它自动把"要检查的事项清单"（测试点）列出来，再细化成"具体怎么检查"（用例），甚至能派人去现场逐项核对（执行），最后给你一份"哪些合格、哪些有问题"的验收报告。

它能帮你解决什么痛点

  • 不用逐行读代码：平台会自动扫描被测软件的源代码，找出它都有哪些功能（登录、发消息、查数据……）。
  • 测试点不遗漏：每个功能会自动展开成多个"检查角度"（正常用、乱用、安全、边界），减少人想不全的情况。
  • 用例可复用、可追溯：每一条测试点都能对应回它来自哪个功能，方便日后回归和审计。
  • 一键出报告：分析、生成用例、执行、出报告可以串成一条流水线，少做重复手工活。

一句话定位

读代码 → 提功能 → 列测试点 → 写用例 → 执行验证 → 出报告

第二章　整体架构长什么样

你可以把整个平台想象成一家"测试工厂"，里面有几间不同的车间，还有一个存放资料的仓库和一间出报告的办公室。

① 入口前台（Web 服务）

对外提供一个统一的服务地址（默认 http://本机:8000）。所有"分析 / 生成 / 执行 / 报告"的操作都从这里我们下达指令。它像是工厂的"调度中心"。

技术名：FastAPI 接口
② 读图车间（代码分析）

专门"读"被测软件的源代码，自动识别它有哪些功能（接口、页面、业务函数等）。它不靠人眼，而是用程序解析代码骨架。

技术名：code_analyzer
③ 出题车间（测试点 / 用例）

把"功能"展开成"要检查的事项"（测试点），再细化成带步骤、带优先级的"测试用例"。这是工厂的"出题组"。

技术名：_ComprehensiveBuilder / case_generator
④ 验收车间（执行器）

把用例真正"跑"一遍：去被测系统上发请求、看返回对不对，记录每一条是通过还是失败。对应"派人去现场核对"。

技术名：executor
⑤ 出报办公室（报告）

把执行结果汇总成报告，可看网页版，也能导出成 Excel / Word / PDF，方便分发和存档。

技术名：reporter / full_report / exporters
⑥ 资料仓库（数据库）

一个本地的"档案柜"（单个文件数据库），存放项目信息、功能清单、用例、每次执行结果、报告等。所有车间共用它记台账。

技术名：SQLite（test_accel.db）
通俗说（车间与仓库）：前台接单 → 读图车间画功能图 → 出题车间列检查清单 → 验收车间现场核对 → 办公室出验收报告；中间所有图纸、清单、核对记录都放进同一个档案柜，随时可查、互不丢失。

两个"外派小组"（技能 / Skills）

除了工厂本身，还有两个可独立外派的小组，专门配合平台干活，也是你（通过 AI 助手）最常用到的操作入口：

  • 拉代码小组（qa-code-pull）：负责把被测软件的代码"搬到"本地、并切到指定版本。搬完后还会给文件夹上"只读锁"，防止被误改。
  • 出测试点小组（qa-test-points）：负责在本地的代码上"读图 + 出题"，生成测试点清单（以及功能点追溯表）。它不碰代码仓库，只读取。

第三章　核心概念小词典

下面这些词会贯穿全文。每个都先用大白话讲，再给一个技术对应，方便你以后和开发对齐。

功能点（Functional Point，简称 FP）
通俗说：软件"会做的一件事"。比如"用户登录""发送聊天消息""查询余额"。

平台扫代码时自动发现的功能。分四类：接口网页背后的服务入口、页面前台能打开的页面、组件页面上可点击的部件、业务函数后台核心计算逻辑。每个功能点有一个稳定编号 fp_id。

测试点（Test Point，简称 TP）
通俗说：针对某个功能，"要核对的一件事"。比如"用对的账号能登录成功""没填密码应该被拦下"。

比功能点更细。一个功能点会展开成多条测试点（如正常、安全、边界等不同角度）。每个测试点带编号 TP-001…，并能指回它来自哪个功能点。

测试用例（Test Case，简称 case）
通俗说：把"要核对的事"写成"具体怎么做 + 预期结果"的操作单。

在测试点基础上补充：前置条件、操作步骤、优先级（P0~P3）、预期结果。这是真正可以派人去执行的一张"工单"。

范围 / 维度（Scope）
通俗说：这一轮"重点检查哪些角度"。

四个行为角度：正常（该用时能用）、异常（出错时别崩）、安全（没权限别放行）、边界（参数乱填别出错）。另有"接口"是按来源筛选（只挑"网页服务入口"类测试点）。详见第八章。

标签：全量 / 更新
通俗说：这条测试点是"整套都查"还是"只查这次改动的部分"。

全量=代码没动到的部分，做常规全面回归；更新=底层代码这次被改动了，优先回归。标签按"改动的具体代码行"精准判定，不是整文件。

双向追溯（Traceability）
通俗说：任何一条测试点都能查到"它来自哪个功能"，任何功能也能查到"派生了哪些测试点"。

保证"被测的功能都有测试、每条测试都有出处"，不会出现凭空多出来的测试或漏测的功能。系统里用 fp_id 串联。

契约（Contract）
通俗说：功能点和测试点之间"统一的身份证规则"，保证两边对得上。

规定编号怎么生成、字段怎么命名。代码不变，编号就不变，因此多次生成的结果能稳定比对、增量更新。

第四章　功能模块一览

平台按"用途"分成以下几块能力。你可以把它当作工厂里的不同"业务窗口"。

模块（窗口）它负责什么你能拿到的产出
项目管理登记"要测哪个软件"：名字、代码地址、分支、访问地址、登录方式。项目档案（一条记录）
代码分析扫描代码，找出全部功能点（接口/页面/组件/业务函数）。功能点清单（可追溯）
增量对比对比两个版本，找出"新增 / 改动 / 删除"了哪些功能。变更摘要 + 功能差异
测试点生成把功能点展开成测试点，可按范围筛选，打"全量/更新"标签。测试点清单（含追溯）
用例生成把测试点细化成带步骤、优先级的测试用例；支持人工审核。用例清册（Markdown/JSON）
执行把用例真正跑一遍（可全量、可筛选、可后台、可中断）。每条用例的通过/失败结果
报告汇总结果：统计、趋势、不稳定项识别、覆盖率；可导出多种格式。网页报告 / Excel / Word / PDF
冒烟检查快速确认"被测软件有没有启动、能不能登录"，像开工前的通水通电检查。通断结论
通俗说（模块 = 窗口）：你去办事大厅，每个窗口办一类事——登记窗口（项目）、读图窗口（分析）、比对窗口（增量）、出题窗口（测试点/用例）、验收窗口（执行）、汇报窗口（报告）、巡检窗口（冒烟）。它们共享同一个档案柜（数据库），所以信息连贯。

第五章　一条测试任务怎么流转（数据流转）

下面用一条最完整的链路，说明"从一段代码"到"一份报告"中间经历了什么。这就是平台的核心数据流。

步骤 1
备好代码
拉代码小组把被测代码搬到本地并锁定版本
→
步骤 2
读功能
读图车间扫描代码，得出"功能点清单"
→
步骤 3
列测试点
出题车间把功能点展开成"测试点"（带范围/标签）
→
步骤 4
写用例
测试点细化成"测试用例"（步骤/优先级/预期）
步骤 5
去执行
验收车间逐条跑用例，记录通过/失败
→
步骤 6
出报告
汇报办公室汇总成验收报告
→
全程
记台账
每一步结果都写入数据库，可随时回查

每一步的"输入 → 输出"

步骤输入（原材料）输出（产物）存到哪里
1 备好代码代码仓库地址、目标版本本地代码副本（只读）本地文件夹
2 读功能本地代码功能点清单（含 fp_id）数据库·功能点表
3 列测试点功能点 + 范围设定测试点清单（含来源/标签）测试点 JSON / 文档
4 写用例测试点测试用例（步骤/优先级）数据库·用例表 + 清册文件
5 去执行用例 + 被测系统地址每条用例的通过/失败数据库·执行记录表
6 出报告执行记录验收报告（网页/文档）报告目录 + 数据库·报告表
关键点（追溯不断链）：因为每一步都用统一的 fp_id 串联，所以最终报告里的"某条失败用例"，可以一路反查到"它对应的测试点 → 来自哪个功能点 → 在代码的哪个文件"。这正是"双向追溯"的价值，也是它和普通"跑一遍脚本"最大的区别。

第六章　怎么使用这个平台

平台目前有两种使用方式。对非开发人员，方式一最省心。

方式一：通过 AI 助手（推荐，日常用法）

你不需要自己敲命令。只要对 AI 助手说清楚意图，它会调用两个"外派小组"依次完成：

  1. 先说"去把代码准备好"：例如"拉取 research-agent 仓库的 test-20260907 版本"。助手会启动"拉代码小组"，把代码搬到本地并上只读锁。
  2. 再说"生成测试点 / 跑测试"：例如"基于完整代码生成全部测试点，范围用默认"。助手会启动"出测试点小组"，产出清单和报告。
通俗说：你像在公司里对助理说"去把 X 项目的图纸拿来、列出验收清单、跑一遍出报告"，助理背后调用的是这两个自动化小组。你只管提要求和看结果。

方式二：直接操作平台（技术/进阶用法）

平台本身是一个运行在本机的服务（默认地址 http://本机:8000）。启动后用"接口"（网址指令）下达任务，例如"分析项目""生成用例""执行""出报告"。这通常由开发或自动化流水线使用。

  • 启动：运行平台自带的启动脚本（start_platform.sh），服务就在 8000 端口待命。
  • 下达：通过"接口地址"触发对应动作，例如"对项目 2 执行全部用例并出报告"。

开关与配置（在 .env 文件里）

平台有很多"总开关"，写在名为 .env 的配置文件里。非开发人员一般不用改，了解即可：

开关默认意思是
人工审核门（REVIEW_GATE）开生成的用例需人工点"通过"才执行；关掉则全自动跑到出报告。
AI 增强（LLM_ENHANCE）开读代码时是否借用 AI 补全描述；关掉则纯靠程序读结构。
动态探测（ENABLE_DYNAMIC_PROBE）关执行时是否真去被测系统发请求核对；关掉只做"静态判定"。
真实浏览器（ENABLE_BROWSER）关是否用真实浏览器验证页面；关掉则页面类只做"可达性判定"。
并发度（EXEC_MAX_WORKERS）4同时跑几条用例，数字越大越快（但本机压力越大）。

下一章汇总"你提供什么、最终得到什么文件"。

第七章　你提供什么 / 得到什么

你（或助手）需要提供

  • 被测对象：软件代码仓库地址 + 要测的版本（分支/提交号）。
  • 访问信息（可选）：被测系统的网址、登录账号（放配置里，不写进代码）。
  • 范围要求（可选）：这轮重点查"正常+边界"还是"全部"，要不要只查"接口"类。

平台最终产出的文件

产物内容给谁看
测试点清单（TEST_POINTS_NEW.md / .json）逐条测试点，带"全量/更新"标签和来源功能点测试设计人员
功能点追溯表（FUNCTIONAL_POINTS.md）功能点 → 测试点 的对应矩阵，证明覆盖无遗漏测试经理 / 审计
新旧对比（TEST_POINTS_COMPARE.md / .html）这次和上次生成的差异，便于看增量项目相关方
用例清册（TEST_CASES.md / .json）可执行的测试用例（步骤/优先级/预期）执行人员
验收报告（VERIFICATION_REPORT / 趋势 / 覆盖率）通过失败统计、结论风险、趋势图、覆盖率PM / 领导
可分发报告（xlsx / docx / pdf）同上内容的办公格式，便于转发存档全员
通俗说：你给"图纸 + 想查的重点"，平台还你"验收清单 + 逐条核对结果 + 一份能转发的验收报告"。清单和报告都能溯源到图纸上的具体位置。

第八章　"范围"和"标签"怎么理解

这两个是你在提需求时最常遇到的设定，单独讲清楚。

一、范围（Scope）：这轮重点查哪些"角度"

平台把测试点按"行为角度"分成四类，可单选或多选组合：

取值查的是什么举例
正常功能该用时能不能用用对的账号能登录成功
异常出错时会不会崩 / 报错友不友好查一个不存在的订单返回 404 而非崩溃
安全没权限会不会被拦住不带登录凭证访问被拒（401/403）
边界参数乱填 / 缺失会不会出错必填项为空被拒（400/422）

另有 接口 这一项，它不是新的角度，而是"按来源挑"：只保留"网页服务入口（HTTP 接口）"这一类测试点。它可以和上面四个角度组合，比如"正常 + 接口"= 只看接口类里的正常测试点。

容易误解的点："接口"不是"额外多生成一类测试点"，而是从已生成的测试点里筛出接口来源的那部分。这样和你之前在线上对话环境里已经验证过的"接口用例"能对上，不重复造轮子。

当前默认范围：正常 + 边界。（即默认重点查"功能可用性"和"参数边界"，不默认查安全/异常——如需更全面就说"全部"。）

二、标签（Tag）：全量 / 更新

标签含义什么时候用
全量代码没改动的部分，做常规全面回归每次都包含，作为基线
更新底层代码这次被改动的具体位置，优先回归对比两个版本时才会出现

"更新"的判定很精细：不是整文件变动就算更新，而是具体哪一行代码被改，只有依赖那行代码的测试点才标"更新"。这样你能精准聚焦"这次改动到底影响了哪些检查项"。

下一章讲平台的"能力边界"，便于你规划优化方向。

第九章　当前的边界与注意事项

为了让后续优化讨论更准，这里如实说明平台现在能做什么、还不能做什么。

已具备的能力

  • ✅ 自动读代码、提取功能点（接口/页面/组件/业务函数四类的全面覆盖）。
  • ✅ 测试点按"正常/异常/安全/边界/接口"多维度展开，覆盖率可统计。
  • ✅ 测试点 ↔ 功能点双向追溯，孤儿（无出处测试点）恒为 0。
  • ✅ 全量 / 更新双标签、精确到代码行级别的改动识别。
  • ✅ 用例生成、人工审核门、执行（可筛选/后台/中断）、多种格式报告。
  • ✅ 代码仓库只读管控（拉取前锁只读、拉取时临时读写、拉完恢复只读）。

当前还较弱 / 待补强的地方

  • ⚠️ 执行以"探活级"为主：默认只做轻量核对（确认接口在、能调用），还不是完整的"真人点页面"式 UI 验证。真实浏览器验证需要开启开关并装好浏览器环境。
  • ⚠️ 没有面向人的网页界面：目前平台靠"接口指令"或"AI 助手"操作，没有能给普通测试人员直接点选的图形界面（前端目录暂为空）。
  • ⚠️ 同步执行：多数操作是"下达后等结果"，要接流水线做"部署后自动触发"还需进一步异步化与调度。
  • ⚠️ 鉴权/账号依赖配置：要真去线上核对，需在被测系统可用、且账号信息配置正确的前提下。
  • ⚠️ 基线版本需有效：打"更新"标签依赖两个版本都能正确解析；若版本号失效，会全部标成"全量"（系统会给出醒目提醒）。
给优化讨论的提示：如果你后续想"加功能 / 改体验"，上面"待补强"几乎就是候选清单。例如：① 做一个人人能点的网页界面；② 把"真人浏览器验证"默认打开；③ 接发布流水线实现"部署完自动跑一遍"。你可以指定任意一条，我们细化方案。

第十章　常见问题与术语对照

常见问题（FAQ）

  • Q：我完全不会写代码，能用吗？
    A：能。你通过 AI 助手用自然语言提要求即可（方式一）。助手背后调用自动化小组完成。
  • Q：测试点和用例有什么区别？
    A：测试点是"要核对的一件事"（想法），用例是"具体怎么做 + 预期结果"（操作单）。一个测试点通常对应一条用例。
  • Q：为什么有的测试标"更新"、有的标"全量"？
    A："更新"是这次代码改动波及的检查项，优先回归；"全量"是没改到的，做常规回归。
  • Q："接口"范围会不会多生成测试？
    A：不会。它只是从已生成的测试点里筛出"网页服务入口"这一类，对应你线上已验证过的接口用例。
  • Q：报告能发给不懂技术的人看吗？
    A：能。报告有网页版，也能导出 Excel / Word / PDF，含通过失败统计和结论风险，适合转发。
  • Q：如果代码仓库被改坏了怎么办？
    A：平台在拉取代码前会给文件夹上"只读锁"，只在拉取那一刻临时放开，拉完立即恢复，降低误改风险。
