## 二、通俗说明（给非技术人员）

> 这一节用大白话解释上面那些"技术行话"到底在管什么、为什么要有这些规矩。

**一句话总览**：我们给这个测试平台立了一套"自动化质检流水线"。每写一行代码、每改一次功能，都有机器自动帮我们检查"有没有写歪、有没有踩坑、有没有泄密"，不合格就不让提交、不让合并。

逐项翻译成人话：

- **架构分层（A1–A3）**：把代码分成"地基 / 引擎 / 门面"三层，规定好谁可以找谁帮忙、谁不能越级。就像公司里"基层干活、中层协调、前台接客"，基层不能反过来指挥前台，否则组织就乱了。这能保证核心引擎将来能被别的项目直接拿来用，不用重写。

- **测试点必须带"执行层"标签（A4、E5）**：每个测试用例都要标明"该用接口测还是用浏览器界面测"。如果选了浏览器但实际只能走接口，系统会自动改走接口并打标记——避免"以为测了其实没测到"。

- **枚举只在一处定义（E1–E3）**：项目里有一份"标准字典"（比如状态只有"通过/失败"、范围只有"正常/异常/安全/边界"），所有代码都去这本字典里查，不允许自己另写一份。这样改一个词，全项目立刻统一，不会出现"同一件事十个写法"。机器还会反过来查：字典里定义了但没人用的词，会提醒你（可能是预留的，不一定是错）。

- **统一门禁（Q1）— 八道关卡一次过**：提交前机器连跑八关——密钥扫描、代码风格、格式、枚举合规、架构合规、类型检查、安全扫描、自动化测试。任何一关没过，提交就被拦下，并告诉你卡在哪一关。

- **代码风格与复杂度（Q2–Q3）**：统一用双引号、统一缩进；并且**规定一个函数不能太长太绕**（圈复杂度 ≤10），防止出现"几百行谁都看不懂"的"上帝函数"。

- **存量豁免（Q4–Q5）是"历史欠债"**：项目里有一部分老代码写得比较随意，我们暂时允许它们"免检"某些规则，但**这只是给老文件的宽限，新写的代码必须严格达标**。相当于"老人过渡、新人从严"。

- **安全扫描（Q6、S1–S4）**：自动扫描代码里有没有常见安全漏洞（比如明文密码、危险系统调用）。密码、密钥一律不进代码库，只放在本地配置里；少数误报项必须写上"此处为何安全"的备注才放行。

- **测试与覆盖率（Q7–Q8）**：每次提交都要跑自动化测试且必须全绿。**目前的覆盖门槛（5%）很低**，只是保证"别比现在更差"，长远目标要提到 60% 以上——这条是"防倒退"而非"高标准"。

- **入库红线和协作流程（S1–S5、P1–P6）**：第三方被测系统的代码、密码、运行产生的数据库都不允许提交进代码库（防止泄密和仓库膨胀）。每次提交和合并都自动跑质检；动到架构 / 字典 / 服务化这类大事，必须先写一份"决策说明"（ADR）再动手；机器人生成代码也必须先过质检才能交付。

- **服务化定位（V1）**：这个平台将来不是孤立工具，而是要像"能力中台"一样被别的系统远程调用、并在每次发布后自动触发验证。所以代码要刻意保持"薄门面 + 厚引擎"的结构，方便复用。

## 三、不足分析与改进建议

> 以下是对当前规范体系的诚实评估。先列**现状不足**（带证据），再给**建议新增 / 补强的规范**（含可落地的要点）。

### 3.1 当前不足（按严重度排序）

| 编号 | 薄弱环节 | 现状证据 | 风险 |
|---|---|---|---|
| D1 | **覆盖率门禁形同虚设** | `fail_under=5`，实测仅 5.25%，绝大多数模块 0% 覆盖（如 full_report 235 行全 0%）。门禁无法拦截"删掉关键逻辑"类回归。 | 质量门禁最弱的一环，实际只防"变负"，不防"变糟"。 |
| D2 | **存量豁免面过大** | `per-file-ignores` 豁免 ~13 个模块（executor/batch_store/reporter/browser/diff_analyzer/analytics/project_manager/auth/smoke/exporters/llm_client 等）；mypy 对 5 个上帝模块 `ignore_errors=true`。即**项目主体处于"免检"状态**。 | "标准"只约束少数新文件，整体代码质量未真正达标，且易形成"新人从严、老人免检"的双标印象。 |
| D3 | **类型安全等级低** | mypy 仅 basic（`disallow_untyped_defs=false`），且 5 模块整体忽略错误；无 `strict`。 | 类型错误（如 None 误用、返回值错位）难在编译期捕获，易在运行时爆雷。 |
| D4 | **无依赖锁定 / 供应链安全** | `pyproject.toml` 声明依赖未锁版本；`requirements.txt` 存在但无 lock 文件；仅有 bandit 静态扫描，**无依赖漏洞扫描（pip-audit / safety）**、无 SBOM。 | 某天某个第三方库发版带漏洞或被投毒，部署即中招，且难以复现构建。 |
| D5 | **无密钥预提交扫描** | 仅靠 `.gitignore` 排除 `.env`；**无 gitleaks / trufflehog 等密钥扫描 hook**。一旦有人把密钥临时写进 `.py` 提交，门禁不拦。 | 凭据意外入库（即便后续删提交，历史仍可能泄露）。 |
| D6 | **无提交信息 / 分支 / PR 规范** | `CONTRIBUTING.md` 未规定 commit message 格式、分支命名、PR 描述模板。 | 提交历史混乱，难以追溯"为什么改"，Code Review 无抓手。 |
| D7 | **无代码评审 / 审批门** | 仅规定"AI 生成须过门禁"，无"至少 1 人审批""CODEOWNERS"要求。 | 单人 / 机器人直推主干，缺乏第二双眼睛，错误易上线。 |
| D8 | **服务化但缺认证 / 鉴权 / 限流规范** | `V1` 定位为"被 testhub 远程调用 + 流水线触发"的独立服务，但 `ARCHITECTURE/CONTRIBUTING` **未定义 API 认证方式（token/JWT）、RBAC、速率限制**。 | 对外暴露的服务若无鉴权，等于把执行能力（含浏览器操作）向未授权方敞开。 |
| D9 | **无 API 契约 / 版本规范** | 端点持续演进，但无 OpenAPI 要求、无版本前缀、无"破坏性变更须 ADR"的机器约束。 | 调用方（testhub / 流水线）易因接口漂移而断连。 |
| D10 | **无统一错误处理 / 日志规范** | 无"结构化 JSON 日志 + 请求 ID""错误响应统一结构""禁止返回堆栈"等规定。 | 出问题时难以排查；错误可能泄露内部细节。 |
| D11 | **无数据库迁移 / 回滚规范** | SQLite schema 有变更但无迁移工具约束、无向下回滚脚本约定。 | 升级失败难回退，数据损坏风险。 |
| D12 | **测试规范薄弱** | 仅"pytest 全绿"；无"新端点必须配套测试""单测/集成测试比例""集成测试禁止 mock 服务层"等要求。 | 关键路径可能长期无测试守护。 |
| D13 | **CI / 分支保护未真正启用** | `guard.yml` 已就绪，但用户尚未在 GitHub 开启 Actions 开关、未设分支保护。 | 远程门禁当前是"纸面防线"，本地漏跑即无人拦截。 |
| D14 | **无性能 / 资源 / 可观测性规范** | executor 会起真实浏览器，但无超时、并发上限、资源清理、健康检查（`/health`）、指标导出规定。 | 批量执行时可能资源耗尽；服务不可观测，故障难发现。 |

### 3.2 建议新增 / 补强的规范

> 每条给出「规范名称 / 建议要点 / 落地方式」，按优先级排列。

**P0（立即补，低成本高收益）**

- **N1 密钥预提交扫描规范**
  - 要点：pre-commit 增加 `gitleaks` / `trufflehog` 扫描，命中高置信凭据即阻断；`.env` 之外也拦"代码里写死 token/密码"。
  - 落地：在两份 `.pre-commit-config.yaml` 的 local hook 中追加密钥扫描步骤（或并入 `gate_all.py` 第 0 环）。

- **N2 提交信息 / 分支 / PR 规范**
  - 要点：采用 Conventional Commits（`feat:`/`fix:`/`refactor:`/`docs:`/`chore:`）；分支命名 `type/short-desc`；PR 模板含"变更摘要 / 影响范围 / 门禁结果 / 测试证据"。
  - 落地：新增 `CONTRIBUTING.md §7` + 仓库 `.github/PULL_REQUEST_TEMPLATE.md` + `commitlint` 配置。

- **N3 启用远程门禁 + 分支保护**
  - 要点：在 GitHub 开启 `guard.yml` Actions 开关；对 `main`/`master` 设保护，要求 `guard` 检查通过 + 至少 1 审批才允许合并。
  - 落地：用户侧操作（文档已指引），建议写入交付清单并截图确认。

**P1（本迭代补，关系到"独立服务"成立）**

- **N4 服务认证 / 鉴权 / 限流规范**
  - 要点：对外端点必须鉴权（项目级 API Token 或 JWT 短时效 + 服务端刷新）；按项目做 RBAC（只读 / 执行 / 管理）；统一速率限制（如 60 req/min）；401 返回标准结构。
  - 落地：新增 `ARCHITECTURE.md §7 安全接入` + `service/` 中间件 + `CONTRIBUTING.md` 补充；门禁可加"新增端点必须带鉴权装饰器"检查。

- **N5 API 契约与版本规范**
  - 要点：路由加 `/api/v1/` 前缀；提供 OpenAPI（`/openapi.json`）；任何破坏性变更须走 ADR 并标注废弃期。
  - 落地：`ARCHITECTURE.md §4` 增"API 契约铁律"；CI 可选对比 OpenAPI diff。

- **N6 统一错误处理与日志规范**
  - 要点：结构化 JSON 日志携带 `request_id`；全局异常处理器返回 `{code,message}` 规范结构，**绝不包含堆栈 / 内部路径**；敏感字段（密码 / token）不落日志。
  - 落地：新增 `backend/service/` 错误处理中间件 + `LOGGING_STANDARD.md`。

- **N7 数据库迁移与回滚规范**
  - 要点：schema 变更一律走带版本号的迁移脚本（如 `migrations/000N_*.sql`）并配套 down 脚本；生产用事务，失败可回滚。
  - 落地：定义迁移脚本命名 / 目录约定（可复用现有 `migrate_enums.py` 思路），写入 `ARCHITECTURE.md §8`。

**P2（中短期，抬升真实质量）**

- **N8 覆盖率从"防倒退"升级为"增量强制"**
  - 要点：引入**增量覆盖率**（diff coverage）门禁，要求新增 / 修改代码行覆盖率 ≥80%；`fail_under` 随重构推进分阶段抬到 60%。
  - 落地：在 `gate_all.py` 第 7 环接入 `pytest-cov` 的 diff-coverage 插件，或独立 `coverage` 门槛策略。

- **N9 存量债务"配额收缩"机制**
  - 要点：把 `per-file-ignores` / mypy `ignore_errors` 列为"技术债预算"，设季度目标逐文件清除；新增 backend 模块一律严格，禁止再扩大豁免清单。
  - 落地：`ARCHITECTURE.md §5` 维护"债务看板"，门禁可加"新增文件不得出现在豁免名单"检查。

- **N10 mypy 渐进 strict**
  - 要点：新模块要求 `disallow_untyped_defs=true`；逐步把上帝模块从 `ignore_errors` 改为 `warn_unused_ignores` 收敛。
  - 落地：分阶段改 `pyproject.toml [tool.mypy]` overrides。

- **N11 依赖锁定与供应链扫描**
  - 要点：用 `pip-compile` / `uv` 生成 lock 文件并提交；`gate_all.py` 增加 `pip-audit` 环节（阻断已知 CVE 依赖）。
  - 落地：CI 与本地门禁第 8 环（或并入现有门禁）。

- **N12 测试金字塔与必备测试规范**
  - 要点：规定"新增端点必须配套单测 + 至少 1 条集成测试"；集成测试用真实 DB（事务回滚）不得 mock 服务层；前端/执行类加冒烟。
  - 落地：`CONTRIBUTING.md §8` 测试规范 + 门禁统计测试数趋势。

**P3（能力加固，配合服务化）**

- **N13 性能 / 资源 / 可观测性规范**
  - 要点：执行任务设超时与并发上限；批量执行资源清理（浏览器 / 队列）；提供 `/health`、`/ready` 健康检查与基础指标端点。
  - 落地：`ARCHITECTURE.md §9` + `service/` 健康端点。

- **N14 代码评审与 CODEOWNERS**
  - 要点：要求至少 1 名 owner 审批；关键目录（backend/core、service）设 CODEOWNERS 强制评审。
  - 落地：仓库 `.github/CODEOWNERS` + 分支保护开启评审 requirement。
