# 测试报告写作模板（场景区分版）

> 用途：拿到一个测试任务时，**先用第 0 节判断"该用哪种测试类型"**，再套用对应小节的可填空模板写报告。
>
> 三种核心测试类型（按你之前定义的执行时机）：
> - **版本对比测试** → 多版本差异比对时
> - **全量测试** → 发布前 / 重大变更后
> - **新增功能覆盖测试** → 迭代新增功能时

---

## 0. 场景 → 测试类型 判定表（先读这里）

| 你手上拿到的信息 / 触发场景 | 应采用的测试类型 | 一句话判定特征 |
|---|---|---|
| 两个版本/分支要做 diff，要"看改了什么、有没有回归" | **版本对比测试** | 有明确的 base → target 的 diff |
| 要上线了，或发生架构/DB/跨模块重大变更，要"全量回归把关" | **全量测试** | 门禁性质、要跑全部用例 |
| 本次迭代只新增/修改了部分功能，要"定向覆盖这批增量" | **新增功能覆盖测试** | 只关注增量模块/API/页面 |
| （补充）提测先验证主流程能跑通 | 冒烟测试 | 只跑核心链路 |
| （补充）修完一个 bug 要验证没带出新问题 | 回归测试 | 围绕修复点 + 关联功能 |

**判定优先级（信息冲突时）：**
1. 存在架构/DB/跨模块重大变更 → **全量测试**
2. 有明确 diff 且没有重大变更 → **版本对比测试**
3. 只有增量功能、无 diff 也无重大变更 → **新增功能覆盖测试**

## 1. 版本对比测试报告模板（适用：多版本差异比对时）

**报告头**：项目 ____｜base `____` → target `____`｜环境 ____｜账号 ____｜时间 ____

**一、变更摘要**
- diff 文件数 __ / 提交数 __ / `+__` `-__`
- 关键新增文件：____（含行数）

**二、变更点清单**
| 文件 | 变更类型（增/改/删） | 影响面 | 风险等级 |
|---|---|---|---|
| | | | |

**三、派生测试点**（针对每个变更点写 正常 / 边界 / 异常）
| 变更点 | 正常场景 | 边界场景 | 异常场景 |
|---|---|---|---|
| | | | |

**四、用例与执行结果**
| 用例ID | 测试点 | 预期 | 实际 | 结果(✅/❌) |
|---|---|---|---|---|
| | | | | |

**五、结论**
- 是否引入回归：是 / 否
- 遗留风险：____

## 2. 全量测试报告模板（适用：发布前 / 重大变更后）

**报告头**：项目 ____｜版本 ____｜环境 ____｜时间 ____

**一、测试范围**
- 全量 __ 条用例（功能 __ / 接口 __ / UI __ / 性能 __）

**二、环境配置**
- 地址 ____｜账号 ____｜依赖版本 ____

**三、通过/失败统计**
- 总数 __ / 通过 __ / 失败 __ / 阻塞 __｜通过率 __%

**四、失败明细**
| 用例 | 失败原因 | 是否阻塞发布 | 关联缺陷 |
|---|---|---|---|
| | | | |

**五、发布门禁结论**
- ✅ 可发布 / ⚠️ 有条件发布 / ❌ 不可发布
- 条件/阻断项：____

## 4. 所有类型通用的公共章节（建议都加上）

- **KPI 卡片**：通过率、失败数、总耗时
- **复用 vs 新建占比**（你要求的量化口径）：
  - 按构件：复用 __ / 共 __ ≈ __%
  - 按代码量：复用约 __%、新建约 __%
- **产物清单**：`resp_*.txt` 原文、`shot_*.png` 截图、`EXEC_MONITOR.md` 监控日志路径

### 与 HTML 报告模板的关系
本写作模板是「内容框架」，配合 `report_templates/test_report.html`（页面结构/样式）使用：
把上面填好的内容映射到 HTML 模板的对应章节 `[token]`，即可生成最终可预览的 HTML 报告。
转换入口：`python gen_html_report.py --context <你的context.json> --out report.html`
