## 一、全链路分段（S0 → S7）

```
S0 取码 / 给地址        「拿到被测对象」——代码目录 或 测试地址+账号
      ↓
S1 项目登记 + 代码扫描   upsert_project → scan → SourceFile 索引
      ↓
S2 功能点提取 (FP)       api / page / component / business（+ 运行时 UI 功能点并入）
      ↓
S3 差异打标 (全量/更新)   diff 基线对比 → 每个 FP 打「全量」或「更新」
      ↓
S4 测试点展开 (TP)       正常 / 异常 / 安全 / 边界（+ PRD 派生的业务规则）
      ↓
S5 用例生成 (Case)       TP → Case 1:1，八要素 + UI 优先排序 + 运行时细节富化
======================= 以上为「生成测试用例」范围 =======================
S6 用例执行              接口层真实 HTTP / UI 层浏览器
S7 报告产出              执行结论、追溯、趋势、导出
```

> **一句话现状**：S0–S5 **两条流程都能端到端出用例了**（A1/A2/A3 的成果）；
> 剩下的问题集中在**「生成得准不准」**（S3 静默降级、S2/S5 重复计数）与**「出线之后」**（S6 持久化 / S7 报告）。

## 四、推荐完成顺序（6 批，含依赖与验收）

### 第 1 批 · 「让生成结果可信」（P0，成本最低、收益最高）

| 顺序 | 编号 | 任务 | 为什么排这里 |
|---|---|---|---|
| 1 | **F7** | 增量基线严格校验：**明确指定了 `base/target` 却不可解析 → `EngineError`**；仅「未指定」时才降级全量 | 一行级改动，直接消除**最危险的静默**（错结论无告警） |

**关键依赖链**：`F12 执行落库` → `F15 报告`。**没有落库就没有历史，报告只能出「一次性快照」。**

## 六、如果只做 3 件事（极简建议）

1. **F7 增量基线严格校验** —— 消除最危险的静默。
2. **F5 两路语义级合并** —— 让用例数不再重复计数（你两次点到的问题）。
3. **F12 执行结果落库** —— 让 A3 的执行结论留得下来。

> 这三件做完，平台就从「能生成一批数字」变成「生成的数字可信、且结论留痕」。

## 八、白话总结

- **能生成用例这件事，已经做到了**（两条路都通，A1/A2/A3 之后）。
- 剩下的三个真问题依次是：
  1. **「准不准」**——增量标签会静默失真（F7）、两路合并会重复计数（F5）；
  2. **「有没有留痕」**——跑完的结论不落库（F12），所以出不了报告（F15）；
  3. **「能不能进流水线」**——端点全同步、无 webhook、无监控（F17）。
- 另有几处「配了以为生效」的静默陷阱（F10a）和两处失实 docstring，都是低成本高收益，建议一并做掉。
