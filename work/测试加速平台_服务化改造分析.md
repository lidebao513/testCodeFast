# 测试加速平台（testCodeFast）服务化改造分析

> **文档状态**：规划分析（当前阶段不实际开发，仅梳理事项与影响）
> **生成日期**：2026-09-08
> **分析依据**：实测当前 `work/test-accel` 代码（后端 1829 行 / 11 文件，前端 0 文件，7 张表，裸 SQL）
> **定位变化**：本服务**不再合并进 testhub**，改为独立部署，对外提供两类调用：
> 1. 被 **testhub 远程调用**（能力下沉为微服务）
> 2. 接入**发布流水线**，在每次发布完成后**自动触发启动验证**

---

## 1. 背景与目标定位

### 1.1 定位变化
此前方案（设计文档 §11/§12）基于"合并进 testhub"假设，已不适用。当前目标为**独立服务化**：平台本体保留为自治服务，testhub 与发布流水线通过 API 消费其能力。这带来更低的耦合、独立演进节奏，但也要求补齐服务治理（鉴权、调度、监控、错误处理）。

### 1.2 两个核心用途

| 用途 | 调用方 | 典型场景 | 对接口的诉求 |
|---|---|---|---|
| ① 被 testhub 远程调用 | testhub 后端（内网） | testhub 在分析/测试流程中调用本服务的代码分析、用例生成、启动验证能力 | 稳定 REST API、可鉴权、可异步、结果可回查 |
| ② 接入发布流水线 | CI/CD（GitHub Actions / Jenkins / 内网流水线） | 发布完成事件 → 自动触发对刚发布版本的启动验证 → 回报通过/失败 | 接收发布事件的 webhook、短时效凭证、门禁结果回传 |

### 1.3 与"合并方案"的关键差异
- 不再需要 Django 重写；**保留 FastAPI 栈**，改造成"可被远程调用的服务"。
- 原 §11 规划的 `code_analysis`/`deployment_target`/`accel_skills` 三个 app 的"新建"动作取消（testhub 侧已自行演进，但本服务不再关心）。
- 重点从"代码搬运"转为"**服务治理 + 异步任务 + 触发集成**"。

## 2. 现有架构盘点（实测）

### 2.1 技术栈
- 后端：**FastAPI + uvicorn**，SQLite（`data/test_accel.db`），原生 HTML/JS（前端 **0 文件未实现**）。
- LLM：`openai` SDK（默认 qwen），经 `llm_client.py` 封装；`config.py` 用 `python-dotenv` 注入 `.env`。
- 依赖：`fastapi, uvicorn[standard], python-dotenv, openai, httpx, requests, playwright`。

### 2.2 代码规模
| 项 | 实测 |
|---|---|
| 后端 Python | **1829 行 / 11 文件**（较早期 1091 行有增长，能力在扩充） |
| 前端 | **0 文件（未实现）** |
| 数据表 | **7 张**：`projects, functional_points, cases, skills, runs, reports, change_log` |
| 裸 SQL | 存在于各模块（`cur.execute(...)`），未用 ORM |

### 2.3 模块职责
| 模块 | 职责 | 服务化相关性 |
|---|---|---|
| `code_analyzer` | 读代码结构（AST/正则）抽取功能点（api/page/component） | 核心能力① |
| `diff_analyzer` | 增量对比（base..head）产出新增/变更/删除功能点 | 核心能力① |
| `case_generator` | 确定性生成用例（**不依赖 LLM**） | 核心能力① |
| `executor` | **requests 探活 + 静态文件断言**，**未实际驱动浏览器**（Playwright 仅声明未启用） | 启动验证能力缺口（见 §4.4） |
| `smoke` | 对 target 做存活/探活验证 | 启动验证候选接口 |
| `html_report` / `reporter` | 生成测试报告 | 结果回报 |
| `project_manager` | 项目管理（注册被测目标、配置） | 数据模型基座 |
| `llm_client` / `config` / `db` / `main` | 支撑层 | 需治理改造 |

### 2.4 现有 REST 端点（11 个，均同步执行）
```
GET  /api/health
GET  /api/projects
POST /api/projects/{pid}/analyze            # 全量代码分析
POST /api/projects/{pid}/diff_analyze       # 增量分析
GET  /api/projects/{pid}/change_logs
GET  /api/projects/{pid}/functional_points
GET  /api/projects/{pid}/cases
GET  /api/projects/{pid}/reports
POST /api/projects/{pid}/scan_and_test      # 扫描+测试（长任务）
GET  /api/projects/{pid}/smoke
POST /api/projects/{pid}/smoke
```

### 2.5 关键事实（决定改造重点）
1. **所有长任务端点为同步阻塞**（`analyze`/`scan_and_test`/`smoke` 直接执行后返回）——服务化后必须异步化，否则一个发布验证会占满 worker。
2. **`executor` 不跑浏览器**：当前"启动验证"仅能到接口探活/静态断言级，真实 UI 交互验证缺口明显。
3. **`case_generator` 确定性、不依赖 LLM**：可被流水线稳定调用，无需担心 LLM 抖动。
4. **SQLite + 裸 SQL**：多调用方并发下存在写锁瓶颈与数据竞争。
5. **无鉴权、无 webhook、无任务状态查询**：当前端点均裸奔，缺乏服务治理能力。
6. **前端 0 实现**：服务化后若仅需被远程调用/流水线触发，前端可降级为"可选轻量后台"，优先保障 API。

## 4. 对现有架构的影响

### 4.1 框架层
- **保留 FastAPI**，但需重构 `main.py`：将 11 个端点按域拆分到 `APIRouter`（analyze / verify / tasks / projects），加 `/api/v1` 前缀。
- 引入**依赖注入**（`Depends`）承载鉴权、配置、任务队列连接。

### 4.2 存储层（影响最大）
- SQLite 在"单一用户在笔记本跑"场景下够用，但服务化后存在 **testhub + 流水线 + 手动** 多调用方并发，**写锁会成为瓶颈**。
- **建议**：迁 **PostgreSQL**（与 testhub 一致，便于未来若需数据互通）；过渡期至少引入 `SQLAlchemy`/连接池并显式事务，消除裸 SQL 的数据竞争隐患。
- 迁移影响：现有 7 张表 schema 需 1:1 映射为 ORM 模型；`change_log.fp_ids` 等 JSON 字段在 PG 用 `JSONB`。

### 4.3 执行模型
- 当前 `analyze`/`scan_and_test`/`smoke` **同步执行**——服务化必须改为"**提交即返回 task_id，后台执行，可查询**"。
- 引入任务队列（推荐 **ARQ**（基于 Redis，轻量）或 **Celery**）。任务状态机：`pending → running → success/failed`，支持超时与取消。

### 4.4 启动验证能力缺口（务必正视）
- 当前 `executor` 是 **requests 探活 + 静态文件断言**，**不驱动浏览器**。
- 因此"发布后自动触发启动验证"目前只能做到：
  - ✅ 拉起/指向已发布 target 的 `health_url` 探活（smoke 已支持）
  - ✅ 静态结构/接口存在性断言
  - ❌ **真实 UI 交互、登录流、业务流程验证**（缺 Playwright 真跑）
- **建议**：将 `executor` 升级为可选引擎（探活引擎 + Playwright 引擎），由调用方按场景选择；requirements 已含 `playwright`，无需新增依赖，仅需补执行逻辑。

### 4.5 前端
- 前端 **0 实现**，且服务化后主要消费方是 testhub 与流水线（均非人类 UI）。
- **建议**：前端降级为"可选轻量运营后台"（查看任务、报告），**不阻塞服务化主线**；优先保障 API 与 webhook。

### 4.6 配置与密钥
- 现有 `RA_GIT_URL` 等经 `.env` 注入（不入库，做法正确）。
- 服务化后需：**密钥进 Secret 管理**（Vault / K8s Secret / CI Secret），禁止 `.env` 随镜像；调用方凭证（testhub / 流水线）单独签发，可吊销。

## 5. 对发布流程的影响

### 5.1 流水线需新增的阶段
```
... 构建 → 发布（deploy） → 【新增】调用验证服务 → 等待结果 → 通过则结束 / 失败则门禁
```
- 发布完成事件（如 `deployment_status=success`）触发 `POST /api/v1/verify/webhook`。
- 流水线**异步等待**结果（轮询 `GET /tasks/{id}` 或接收服务回调）。

### 5.2 验证结果回传
- 服务返回标准化 JSON：
```json
{
  "task_id": "v-20260908-abc",
  "target": "research-agent",
  "commit": "a1b2c3d",
  "status": "success | failed | blocked",
  "summary": { "total": 42, "passed": 40, "failed": 2 },
  "report_url": "https://verify.internal/reports/v-20260908-abc",
  "started_at": "...", "finished_at": "..."
}
```
- 流水线据 `status` 决定：成功→继续；失败→**阻断发布并告警**（门禁策略可配置为"阻断"或"仅告警"）。

### 5.3 失败处理
- **阻断 vs 告警**：核心路径建议"阻断 + 通知负责人"；非核心冒烟可"仅告警"。
- 失败详情（失败用例、截图、日志）回传流水线制品（artifact）供复盘。

## 6. 服务接口设计

### 6.1 设计原则
- 版本化（`/api/v1`）、异步任务模型、统一错误响应、幂等性、最小权限。

### 6.2 端点规划（新 vs 既有改造）

| 方法 | 路径 | 用途 | 来源 |
|---|---|---|---|
| GET | `/healthz` | 存活/就绪（区分 liveness/readiness） | 改造 |
| POST | `/api/v1/projects` | 注册/查询被测项目 | 改造自 `/api/projects` |
| POST | `/api/v1/projects/{pid}/analyze` | 提交全量分析任务 → 返回 `task_id` | 改造（异步化） |
| POST | `/api/v1/projects/{pid}/diff_analyze` | 提交增量分析任务 | 改造（异步化） |
| POST | `/api/v1/verify/start` | **启动验证**（流水线/测试用）：传入 target+commit | **新增** |
| POST | `/api/v1/verify/webhook` | **接收发布事件**触发验证 | **新增** |
| GET | `/api/v1/tasks/{task_id}` | 查询任务进度/结果 | **新增** |
| GET | `/api/v1/projects/{pid}/functional_points` | 功能点列表 | 保留 |
| GET | `/api/v1/projects/{pid}/cases` | 用例列表 | 保留 |
| GET | `/api/v1/projects/{pid}/reports` | 报告列表 | 保留 |
| POST | `/api/v1/projects/{pid}/smoke` | 提交探活验证任务 | 改造（异步化） |

### 6.3 核心 Schema 示例

**发布流水线触发启动验证**
```json
POST /api/v1/verify/webhook
{
  "event": "deployment.success",
  "target": "research-agent",
  "env": "staging",
  "commit": "a1b2c3d",
  "base_url": "https://staging.internal/research-agent",
  "health_url": "https://staging.internal/research-agent/api/v1/health",
  "callback_url": "https://ci.internal/hooks/verify-cb"
}
→ 202 Accepted
{ "task_id": "v-20260908-abc", "status": "pending",
  "poll_url": "/api/v1/tasks/v-20260908-abc" }
```

**testhub 提交分析任务**
```json
POST /api/v1/projects/{pid}/analyze
{ "scope": "full", "engine": "ast" }
→ 202 { "task_id": "a-...", "status": "pending" }
```

**任务状态查询**
```json
GET /api/v1/tasks/{task_id}
{ "task_id":"v-20260908-abc", "status":"running",
  "progress": 0.6, "stage":"executing_cases",
  "result_url":"/api/v1/tasks/v-20260908-abc/result" }
```

### 6.4 任务状态机
```
pending → running → success
                ↘ failed (可重试 → running)
                ↘ cancelled
```
- 超时（如 30min）自动置 `failed` 并告警。
- 结果幂等：同一 `(target, commit, scope)` 重复提交返回既有 `task_id`。

## 7. 部署与运行方式

### 7.1 容器化
- 提供 `Dockerfile`（python:3.12-slim + 安装 `playwright` 浏览器依赖）；镜像不含 `.env`/密钥。
- 通过环境变量注入配置（DB 连接、Redis、密钥引用）。

### 7.2 编排与进程托管
- 推荐 **Kubernetes**（与内网大模型/测试平台同集群）：Deployment + Service + 可选 HPA。
- 单机过渡可用 **systemd** 托管 uvicorn + worker（任务队列 consumer）。
- 端口：API 固定（如 8080），与 testhub（8000）、research-agent（8010）错开。

### 7.3 配置与密钥
- 配置：`CONFIG_MAP`（DB/Redis/日志级别）；密钥：`SECRET`（DB 密码、调用方 API Key、Git token 引用）走 Secret 管理。
- 沿用现有"密钥不入库"原则：Git token 仅存引用（如 `cred:<id>`），明文在 Secret 中。

### 7.4 网络拓扑
```
[发布流水线] --webhook--> [验证服务 /api/v1/verify/webhook] --回调--> [流水线]
[testhub]    --REST----> [验证服务 /api/v1/*]                  --结果--> [testhub]
[验证服务]   --驱动-----> [被测目标 base_url/health_url]（已发布实例）
```
- 内网互通；testhub 与验证服务间建议 **mTLS 或内网 API Gateway**。

## 8. 触发与调度机制

### 8.1 触发源
1. **发布流水线 webhook**（主用途②）：`deployment.success` 事件 → `verify/webhook`。
2. **testhub 远程调用**（主用途①）：按需 `POST analyze/verify/start`。
3. **手动/定时**（可选）：运营后台触发、每日基线验证。

### 8.2 调度与并发
- 任务入队（Redis/Broker），固定并发 worker 数（如 4），避免压垮被测环境。
- **队列优先级**：发布验证 > testhub 实时分析 > 定时基线。

### 8.3 幂等与去重
- 以 `(target, commit, scope)` 为去重键：同一发布重复事件只跑一次。
- 支持"强制重跑"参数覆盖去重。

## 9. 鉴权

| 调用方 | 推荐方案 | 说明 |
|---|---|---|
| testhub | **mTLS** 或 **OAuth2 client-credentials**（长期凭证） | 内网服务间，证书/客户端密钥，可吊销 |
| 发布流水线 | **短时效 Token**（CI 注入，每次构建轮换） | webhook 带 `Authorization: Bearer <ci-token>` |
| 内部管理/后台 | 账号 + RBAC（可选） | 仅运营人员访问 |

- **凭证不入库明文**：沿用现有 `RA_GIT_URL` 注入模式，密钥仅存引用。
- 所有端点（除 `/healthz`）强制鉴权；401/403 统一错误体。

## 10. 错误处理

### 10.1 统一错误模型
```json
{ "error": { "code": "TASK_FAILED", "message": "...", "task_id": "v-...", "retryable": true } }
```

### 10.2 幂等
- 任务提交幂等（同 key 返回既有任务）；重复 webhook 安全。

### 10.3 超时与重试
- 单任务超时（默认 30min）→ `failed` + 告警。
- 瞬时错误（网络抖动、被测服务未就绪）自动重试 N 次（指数退避），就绪探测前置。

### 10.4 部分失败
- 分析/执行中单功能点失败**不整体失败**：记录失败项，汇总到结果，状态按阈值判定（如失败率 > X% 才 `failed`）。

### 10.5 死信与兜底
- 多次失败任务进死信队列，留痕供排查；不被自动丢弃。

## 11. 监控

### 11.1 健康检查
- `/healthz`：liveness（进程活）= 探活；readiness（依赖就绪：DB/Redis/被测可达）= 接流。

### 11.2 指标（Prometheus）
- 任务：`verify_tasks_total{status}`、`task_duration_seconds`、`queue_depth`、`concurrency`。
- 业务：`functional_points_extracted`、`cases_generated`、`verify_pass_rate`。
- 资源：worker CPU/内存、DB 连接数。

### 11.3 日志与追踪
- 结构化日志（JSON），含 `task_id`/`target`/`commit` 便于检索。
- 接入分布式追踪（OpenTelemetry），串联"流水线事件 → 任务 → 执行 → 报告"。

### 11.4 告警
- 服务不可用（readiness 失败）、任务大面积失败、被测 target 连续验证失败 → 通知负责人。
- 门禁失败 → 同步告警发布负责人。

### 11.5 审计
- 记录"谁（调用方）/ 何时 / 对何 target+commit / 触发何种验证 / 结果"，满足合规复盘。

## 12. 实现与架构建议（总览）

### 12.1 技术选型建议
| 维度 | 建议 | 理由 |
|---|---|---|
| Web 框架 | 保留 FastAPI | 已具备，异步友好 |
| 任务队列 | **ARQ**（Redis） | 轻量，契合现有栈；重负载可选 Celery |
| 存储 | **PostgreSQL** | 解决并发写锁，与 testhub 对齐 |
| 容器 | Docker + K8s/systemd | 标准化部署 |
| 鉴权 | mTLS / OAuth2 cc | 内网服务间标准做法 |
| 监控 | Prometheus + OTel | 云原生标配 |

### 12.2 演进路线
```
MVP（可被调用）      ：容器化 + 端点版本化 + 异步化(ARQ) + /healthz + webhook 接收
→ 集成期            ：testhub 调用联调 + 流水线 webhook 联调 + 结果门禁
→ 生产加固          ：PostgreSQL + 鉴权 + 监控告警 + 重试去重
→ 能力深化          ：Playwright 真跑 UI 验证 + 被测目标托管
```

### 12.3 风险与开放问题
1. **启动验证深度**：当前 executor 不跑浏览器，真实 UI 验证需补 Playwright 逻辑（中工作量）。
2. **被测目标可达性**：服务需能访问"已发布实例"的 `base_url/health_url`；若 target 在内网隔离区，需打通网络或支持自拉起。
3. **存储迁移成本**：SQLite→PG 涉及 7 表 ORM 化 + 历史数据迁移。
4. **与 testhub 职责边界**：避免"验证服务"与 testhub 既有 `ui_automation` 能力重复；建议本服务专注"被调用/被触发"的轻量验证，重负载 UI 测试仍归 testhub。
5. **前端取舍**：0 实现前端是否补运营后台，需与 testhub 后台定位对齐，避免重复建设。

---

## 13. 结论
将 testCodeFast 改造为独立服务**技术风险可控**：核心能力（代码分析、用例生成、探活验证）已具备且逻辑解耦（FastAPI 仅耦合于 `main.py`）。主要工作量不在"搬运"，而在**服务治理四件套**——异步任务化、鉴权、监控、触发集成（webhook + 流水线门禁）。当前阶段建议先固化本分析为改造蓝图，待实际开发时按 §3 的 P0→P4 阶段推进，并优先补齐 §4.4 指出的"真实 UI 启动验证"能力缺口，否则"发布后自动验证"将停留在探活层面。
