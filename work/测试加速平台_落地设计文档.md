# 测试加速平台 · 落地设计文档

> 版本：v1.3（定稿）　生成时间：2026-09-06
> 目标：把"代码 → 功能点 → 可执行 case → 执行 → 报告"全链路自动化，沉淀**可复用 skill 资产**，在代码更新时自动派生新 case 并完成全量回归，加速短周期测试。
> **v1.3 修订说明（用户最终拍板）**：① **功能点提取方式定为"读代码结构"（AST 为主）**，LLM 仅作可选增强、可在设置关闭（关闭即纯 AST）；② 确认**增量回归工作流**：首轮全量扫描功能点 → 代码更新后重分析派生新功能点/新 case → 合并入总 case 集 → 执行新 case + 全量回归；③ 锁定 LLM 为 Qwen，模型 `qwen3.7-flash-2026-07-15`，API Key 已写入 `.env`（不进文档/不进 git）；④ v1.2 其余决策（testhub 解耦、Skill 原生自包含、审查门默认开可关、6 阶段分期）维持不变。

---

## 1. 背景与目标
开发频繁快速交付代码，但测试周期短、人力有限。本平台通过自动化链路 + 资产沉淀，让"改完代码即测完"成为可能。

- **首个被测项目**：`research-agent`（从 Codeup 拉取，**只读**，本地部署为 test 环境；平台全程不改其代码、不 push）。
- **后续**：可接入更多被测项目（多 git 配置），覆盖 PC / H5 / Android / iOS。
- **平台与目标的边界**：平台本体（test-accel）与被测项目（targets/*）是**两个独立仓库**；平台只读取目标代码、运行其服务，绝不修改目标工作区。
- **平台独立性**：平台自包含运行；生成的 Skill / 测试项目为平台自有资产，后期不一定在 WorkBuddy 中使用（导出 WorkBuddy 仅为可选、不确定的扩展）。

## 2. 关键决策（已与用户确认）
| 项 | 决策 |
|----|------|
| research-agent 定位 | **被测目标项目，非平台基座**；平台对其只读，本地部署为 test 环境供测试 |
| 技术栈 | FastAPI（后端）+ SQLite（存储）+ 原生 HTML/JS SPA（前端），轻量、易局域网部署，与既有 aiSitePilot / 督办系统一致 |
| 功能点提取方式 | **读代码结构（AST 为主）**：直接解析路由表 / 接口声明 / 页面组件 / 函数签名得出"确定存在的功能点"；LLM 仅作可选增强（可在设置关闭，关闭即纯 AST 结果） |
| LLM | 默认**通义千问（Qwen）**，已锁定模型 `qwen3.7-flash-2026-07-15`，API Key 存于 `.env`；预留切换 DeepSeek，模型配置化，可按项目切换 |
| MVP 范围 | 先做 **PC Web 端**（Playwright 执行）；H5 / Android / iOS 列入**待完成任务追踪**，记录但不实现执行 |
| 归属 | 整体置于 workspace 下 `work/` 项目目录（可选后续推至 Codeup `work` group） |
| 未来迁移 | 后期可能迁移到 **testhub** 项目；技术栈与模块保持**解耦 / 可移植**（LLM、执行器、存储均可插拔），不为迁移提前重度耦合。**合并细则见 §11**（testhub 技术栈已确认为 Django 4.2 + Vue3 + MySQL/SQLite + Celery/Channels） |

## 3. 总体架构
核心链路（详见架构图）：
```
多项目 Git 配置 → 代码分析(读代码结构·AST为主) → 功能点 → Case 生成 / Skill 生成 → 执行 → 报告
                                                        │
                                              资产库(功能点/Case/Skill/报告)
首轮：全量扫描功能点 + 生成 case → 总 case 集 → 全量执行出基线报告
增量回归：git 更新 → 重分析 → 与总功能点集合 diff(新增/变更/删除) → 派生新/变更 case 合并入总集 → 执行新case + 全量回归 → 基线对比报告
```

## 5. 数据模型（SQLite）
- **projects**：id, name, git_url, git_token_ref, branch, type(pc/h5/android/ios), status(active/pending), run_command, health_url, base_url, auth_type(none/form/token), auth_config(json), fixtures(json), port, local_path, created_at
- **functional_points**：id, project_id, commit_ref, file_path, name, description, ftype(page/api/component/flow), review_status(pending/approved), created_at
- **cases**：id, project_id, fp_id, title, steps(json), ctype(e2e/api), script_path, review_status(pending/approved), status, created_at
- **skills**：id, name, description, spec_path, scope(project/global), version, usage_count, created_at, updated_at
- **runs**：id, project_id, case_id, status(pass/fail/error/flaky), screenshot_path, log_path, duration_ms, created_at
- **reports**：id, project_id, batch_id, baseline_report_id, summary(json), html_path, created_at
- **change_log**：id, project_id, commit_from, commit_to, new_fp_ids, updated_fp_ids, removed_fp_ids, created_at

## 6. 核心模块设计

### 6.1 项目管理 project_manager
- 配置多个被测项目的 git 地址 / Token / 分支 / 类型 / 启动命令 / 测试上下文，提供 CRUD。
- **只读拉取**：`git clone` + 定期 `git pull`；绝不 push / commit 目标仓库。
- **本地部署 test 环境**：按 `run_command` 在后台托管目标进程，`health_url` 探活，暴露 `base_url` 给执行器；分配独立 `port`（端口池），避免冲突。
- **进程托管**：start / health-check / stop，日志落盘，超时与异常保护；MVP 单项目串行，后期支持并发队列。
- 只读保障：平台仅读取目标代码与运行其服务，不修改目标仓库任何文件。

### 6.2 代码分析 code_analyzer（→ 功能点）
- **通俗理解（先讲人话）**：所谓"功能点"，就是**从被测项目代码里自动发现的、值得测的东西**。比如分析 research-agent 后，平台发现它"有个登录页、有个发起对话的接口、有个发送按钮"——这些就是功能点。每个功能点对应一条或一组测试用例。平台做的事 = 看代码 → 列出"这系统能干什么" → 逐个生成测试。
- **怎么发现（用户拍板：读代码结构为主）**：
  - **【主】读结构（AST）**：直接解析代码，找出路由表、接口声明、页面/组件、函数——这是"确定存在的东西"，不依赖 LLM、稳定可复现。功能点提取以 AST 结果为准。
  - **【可选增强·可关闭】让 AI 归纳（LLM）**：基于代码语义，总结"这个系统该测什么、边界在哪"，补全单看结构看不出的意图。在设置中关闭后，功能点**仅来自 AST**，LLM 增强不参与。
- **用户最终决策**：功能点提取 = **读代码结构（AST 为主）**。
- **功能点分类（ftype）**：
  - `page`：前端页面（如 `/login`、`/dashboard`）
  - `api`：后端接口（如 `POST /api/chat`）
  - `component`：关键交互组件（如"发送按钮""文件上传"）
  - `flow`：跨页面业务流（如"新建会话 → 发送 → 查看回复"）
- **实例（research-agent 拉取后按实际校正）**：
  - FP1 `page`：登录页 `/login`
  - FP2 `api`：`POST /api/chat` 发起对话
  - FP3 `flow`：新建会话 → 发送消息 → 查看回复
- 输出 `functional_points` 入库，关联 `commit_ref`，初始 `review_status=pending`。

### 6.3 Case 生成 case_generator
- **生成依赖运行时发现**：以 `base_url` + 代码分析得到的路由/接口为输入，LLM 生成可执行步骤（导航 / 操作 / 断言）。
- **类型**：
  - `e2e`（UI，MVP 主用）：Playwright 步骤（goto → click → fill → expect）。
  - `api`（同构支持）：method / url / body / assert，复用 `base_url` 与 `auth_config`。
- **Skill 优先**：生成前先匹配 `skills` 表已有能力，命中则直接套用，未命中再生成并回流（见 6.4）。
- **稳定定位**：优先语义 / 文本 / role 定位，避免易变 xpath，降低 flaky。
- 生成 case 初始 `review_status=pending`。

### 6.4 Skill 生成 skill_generator（核心资产）
- **Skill 是平台自有、自包含的测试能力资产**（不是 WorkBuddy 专属格式）：以 `skill.yaml`（元数据：名称/作用域/触发条件）+ `playbook.md`（步骤规范）+ `helpers/`（可执行脚本）组成，版本化入库（skills 表），`usage_count` 统计复用频次。生成的技能/项目后期不一定在 WorkBuddy 中使用，平台自身即可消费与复用。
- **回流闭环**：高频 / 成功 case → 提炼为 skill；后续 case 生成优先复用，形成"成功案例 → skill → 复用生成新 case"的资产闭环。这是平台核心资产，也是跨项目复用测试能力的载体。
- **导出（可选/不确定）**：未来如需，可额外提供导出为 WorkBuddy `SKILL.md` 的适配层；但非必需，不影响平台独立运行。

### 6.5 执行器 executor
- MVP：Playwright 驱动本机浏览器执行 PC Web case，捕获结果 / 缺陷 / 截图 / 日志。
- **可靠性**：
  - 失败自动重试 N 次，区分 `flaky`（偶发）与真 `fail`。
  - 注入测试上下文（登录态、测试账号来自 `auth_config`/`fixtures`）。
  - 单 case 超时保护，异常归一为 `error`。

### 6.6 报告 reporter
- 聚合 runs → 报告（HTML）：通过率、缺陷列表（含截图）、覆盖的功能点、执行时长。
- **基线对比**：与上一基线报告比较，标出"本次回归新增失败 / 已修复"，直接回答"这次改动有没有引入问题"。

### 6.7 增量回归调度 scheduler
- **触发**：MVP 定时 `git pull` 轮询；后期接 webhook（push 事件）。
- **步骤**：
  1. 拉取更新，记录 `commit_from → commit_to`。
  2. **重分析**目标代码 → 与上次 `functional_points` 集合做 diff（新增 / 变更 / 删除）。
  3. 对**新增 & 变更**功能点生成 / 更新 case（复用 skill）。
  4. 执行：MVP 跑全量；后期支持"变更相关子集 + 全量基线对比"。
  5. 生成报告并与基线对比；`removed_fp_ids` 对应 case 标记停用。
- 落 `change_log`，供前端展示"本次改了什么、测了什么"。

### 6.8 人工审查门 review_gate（可选，默认开启）
- 生成的功能点 / case 进入 `pending`，用户在前端点"通过"才纳入执行；防止低质 LLM 产物误跑。
- 对齐"自动生成 + 验证闭环"与人工抽检习惯。**默认开启**；在设置中关闭后，全链路（功能点 → case → 执行 → 报告）**自动执行到最终报告，无人工卡点**。

### 6.9 前端平台 frontend（模块清单）
- **仪表盘**：项目健康度、最近运行、功能点覆盖率。
- **项目管理**：CRUD + 配置（git / 类型 / 启动命令 / 测试上下文 / 端口）。
- **功能点视图**：按项目列出，支持审查（通过 / 驳回）。
- **执行**：触发全量 / 增量，实时状态（排队 / 运行中 / 完成）。
- **报告**：列表 + 详情 + 截图 + 缺陷 + 基线对比。
- **Skill 库**：浏览 / 版本 / 复用次数 / 导出。
- **设置**：LLM 提供方与模型切换、端口、审查门开关。
- 预留扩展：多端、配置中心、webhook、并发队列。

## 9. 执行计划（分阶段，每阶段结束可运行）
0. **脚手架**：建 `work/` 结构、venv + 阿里云镜像、拉取 research-agent（只读）并探明技术栈与启动方式。

## 10. 风险与开放点
- research-agent 具体技术栈 / 启动命令 / 是否需登录，需拉取后确认（执行阶段探明，写入项目测试上下文）。
- 目标服务本地部署的依赖与端口冲突：由端口池 + 进程托管解决。
- LLM 输出稳定性：功能点 / case 经**人工审查门** + 解析失败降级（纯 AST 结果并标记待补）。
- 执行 flaky：重试 + 稳定定位 + 状态区分（flaky/fail/error）。
- 移动端执行引擎（Appium / XCUITest）留待后续阶段。
- 用户需在执行阶段提供 `QWEN_API_KEY`（及可选 `DEEPSEEK_API_KEY`）。
- 安全：MVP 信任内部目标项目；后期对外部/不可信目标需沙箱隔离。
- **testhub 迁移**：后期可能迁至 testhub 项目，当前以解耦/可移植方式实现（LLM、执行器、存储可插拔），迁移成本可控。**testhub 技术栈已确认 = Django 4.2（后端）+ Vue3/Vite（前端）+ MySQL 8.0（默认，支持 `DB_ENGINE=sqlite3` 平迁）+ Celery + Channels/Daphne + Redis**；合并阶段按 §11 对齐，复用其既有 app 与基础设施，避免重复造轮子。

## 11. 合并到 testhub 的注意事项（后续生成项目时遵循）

> 适用范围：当把"测试加速平台"从独立 FastAPI/SQLite/原生 HTML 实现，**合并进 testhub（Django 平台）**时，按本节执行。MVP 阶段仍按 §2/§4 的独立栈实现，保持解耦；合并阶段才做本节对齐。

### 11.1 合并本质与最大改造点
合并不是"复制粘贴"，而是把平台能力落到 testhub 既有的 Django app 体系。三处技术栈差异是主要改造量：

| 维度 | 独立 MVP（§4） | testhub 现状 | 合并动作 |
|------|---------------|--------------|----------|
| 后端框架 | FastAPI（`main.py` + 模块） | Django 4.2 + DRF（ViewSet/Serializer） | 各模块改写为 Django app + DRF 视图；异步任务走 **Celery**，实时进度走 **Channels/WebSocket** 或前端轮询 |
| 前端 | 原生 HTML/JS SPA | Vue3 + Vite（`frontend/src/views`），全量 vue-i18n（zh/en/ja/ko） | 平台 UI 改写为 Vue3 模块，接入 router/store/api 体系，**必须 i18n 化** |
| 存储 | SQLite（`data/`） | Django ORM；默认 MySQL 8.0，支持 `DB_ENGINE=sqlite3` 平迁 | 数据模型改写为 Django models；先用 sqlite3 模式平迁，再按需切 MySQL |
| 部署 | 单 venv + 后台进程 | `start_dev.sh` / Daphne(:8000) + Celery + 前端 `npm run build` | 复用 testhub 启动脚本，目标服务托管另见 §11.6 |

### 11.2 能力映射：新增 / 复用 / 扩展
**核心原则：先复用 testhub 既有能力，只在缺位处新建 app，绝不双套 case/执行/报告引擎。**

| 测试加速平台模块 | testhub 对应 | 动作 |
|------------------|--------------|------|
| `code_analyzer`（读代码结构 / AST → 功能点） | 无直接对应（testhub 仅"需求文档→case"与"browser-use 探活站点"） | **新建 `code_analysis` app**：静态 AST 抽取与 testhub 的"运行时站点探索"互补，不强行并入 `requirement_analysis` |
| `case_generator`（运行时发现 + Skill 优先 + 稳定定位） | `testcases` 模型 + `ui_automation` 生成逻辑 | **复用** `testcases`；生成逻辑对齐 `ui_automation` 既有 playwright 生成 |
| `skill_generator`（资产闭环：skill.yaml+playbook.md+helpers，版本化） | 无 skill 概念（grep 全仓无 `skill`） | **新建 `accel_skills` app**：平台独有核心资产，必须带入 |
| `executor`（Playwright PC Web） | `ui_automation.playwright_engine`（已含 Playwright/Selenium） | **复用** `playwright_engine`；新增"代码派生 case"专用执行入口，不重写引擎 |
| `reporter`（聚合 + 基线对比） | `reports`（`TestReport`/`ReportTemplate`）+ Allure | **复用** `reports`；基线对比挂 `reports` 扩展字段 |

| `review_gate`（功能点/case 审查门） | `reviews`（评审模板/分配/意见） | **复用** `reviews` 工作流承载审查门 |
| `project_manager`（只读克隆 + 本地部署 + 端口池 + 进程托管） | `projects`（`Project`/`ProjectEnvironment`，含 `base_url`/`variables`） | **扩展** `Project` 或新建 `deployment_target`：补 `git_url`/`git_token_ref`/`branch`/`run_command`/`port`/`health_url`/只读克隆/进程托管 |

### 11.3 必须新建的三个 app（testhub 缺位能力）
1. **`code_analysis`**：AST 功能点抽取（page/api/component/flow 分类）、`commit_ref` 关联、`change_log`（新增/变更/删除 diff）、增量重分析。这是平台区别于 testhub"需求文档驱动"的独有价值。
2. **`accel_skills`**：Skill 资产库（`skill.yaml`+`playbook.md`+`helpers/`）、版本化、复用计数、回流闭环。testhub 全仓无 skill 概念，需原生引入。
3. **`deployment_target`**（或扩展 `Project`）：被测目标服务的**只读 git 克隆 + 本地部署(test env) + 端口池 + 进程托管 + 探活**。testhub 当前不托管被测服务，这是合并时必须新增的基础设施。

### 11.4 LLM 配置对齐
- 复用 `requirement_analysis.AIModelConfig`：模型类型已含 `qwen`（通义千问）、`deepseek`；字段 `base_url`/`api_key`/`model_name`/`role`（`writer`/`reviewer`/`browser_use_text`）齐备。
- 设计文档锁定的 `qwen3.7-flash-2026-07-15` → 新增一条 `model_type=qwen`、`role=writer`、`base_url=https://dashscope.aliyuncs.com/compatible-mode/v1` 的配置即可，**无需自写 `llm_client`**。
- **"可关闭 LLM、纯 AST"** 约定保留：合并后通过"无 active 的 writer/reviewer 配置"即退化为纯 AST，功能点以 AST 结果为准的语义不变。
- API Key 由 `.env` 明文改为入库 `AIModelConfig`（testhub 既有管理界面可维护），`.env` 仅留 `DB_*`/`REDIS_URL`/`SECRET_KEY`/邮件。

### 11.5 用户 / 权限 / 多租户
- 复用 `users`（JWT + Token + Session）与 `ProjectMember` 角色（owner/admin/developer/tester/viewer）。
- `functional_points` / `cases` / `skills` 须带 `project` 归属与创建者，对齐 testhub 既有的"项目—成员"隔离模型。

### 11.6 执行与实时进度
- 执行引擎复用 `ui_automation.playwright_engine`；长任务走 **Celery**，进度复用 `executions` 状态机（`TestRun`/`TestRunCase`/`TestRunCaseHistory`），前端按需轮询或经 Channels WebSocket（参考 `app_automation` 的 `ws/app-automation/executions/<id>/`）。

### 11.7 数据模型迁移映射
| 设计文档模型 | testhub 落点 | 备注 |
|--------------|--------------|------|
| `projects` | `Project`（扩展 git/部署字段）或 `deployment_target` | 复用 `ProjectEnvironment.base_url`/`variables` |

### 11.8 部署 / 端口 / 密钥
- 后端 Daphne `:8000`，前端 `:3000`（testhub 既定）；目标被测服务用独立端口池（§11.3 的 `deployment_target` 管理）。
- `.env` 仅保留 DB/Redis/SECRET/邮件；LLM 凭据入库（§11.4）。
- 目标服务进程托管、探活、日志落盘由 `deployment_target` 负责，超时与异常保护对齐 `core` 的进程管理惯例。

### 11.9 i18n
- 新增 Vue3 模块必须走 `vue-i18n`（zh-hans/en/ja/ko），复用 `frontend/src/locales`，不满足则无法通过合并验收。

### 11.10 合并专属风险
- **重写成本**：FastAPI→Django、原生 HTML→Vue3 是实质重写而非搬运，预算按"端口/模块"估，不因"解耦"而低估。
- **重复能力风险**：case 生成/执行/报告与 `ui_automation`/`api_testing` 高度重叠，**先复用再补差**，禁止出现第二套 case/执行/报告引擎。
- **目标服务托管缺位**：testhub 不托管被测服务，§11.3 的部署管理必须补齐（Docker 化目标 or 后台子进程）。
- **命名/语义冲突**：`functional_points`/`cases`/`skills`/`runs` 在 testhub 各有近似表，迁移时表名与字段须显式对齐，避免与 `testcases`/`executions`/`reports` 语义打架。
- **"纯 AST 关闭 LLM" 约定**：合并后该路径仍须成立（§11.4）。
- **建议落地顺序**：MVP 按 §4 独立实现并验证全链路 → 合并阶段先接入 `AIModelService` + `playwright_engine` + `testcases`/`reports`/`reviews` → 再补三个新建 app → 最后做 Vue3 前端与 `deployment_target`。这样每步都可独立验收，符合 §9 分阶段可运行原则。
