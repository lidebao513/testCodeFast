# 测试执行服务（含浏览器）封装与运行时自愈 · 执行方案

> **文档状态**：架构与执行方案（规划层，当前阶段不实际开发）
> **生成日期**：2026-09-08
> **承接文档**：`测试加速平台_服务化改造分析.md`（§4.4 已指出 executor 不跑浏览器、真实 UI 验证缺口）
> **分析依据**：实测 `work/test-accel` 代码——`executor.py`（131 行，当前为 `requests` 探活 + 静态断言，零浏览器调用）、`llm_client.py`（已封装 Qwen/DeepSeek）、`main.py`（11 同步端点）
> **本方案要解决的核心问题**：把**完整测试执行流程（含浏览器）**封成独立服务、内部统一调度浏览器；并回答——
> ① 执行中出错能否**在服务内同步改代码**自愈？② 是否应**把 WorkBuddy「按问题自动改代码」的能力集成进服务**？

---

## 0. 结论先行（给决策者的 30 秒）

| 问题 | 结论 | 一句话理由 |
|---|---|---|
| **Q1：执行出错时能否在服务内同步改代码修复？** | **不允许「同步原地改运行中的代码」，允许「带护栏的、异步的、版本化的测试资产修补」** | 同步改运行中的验证代码 = 破坏门禁可信度 + 无回滚 + 不可审计 + 易死循环；绝大多数失败根本不需要改代码 |
| **Q2：是否集成 WorkBuddy 自动改代码能力？** | **要集成，但只能作为「带外（out-of-band）的自动建 PR 机器人」，绝不能嵌进实时门禁里同步打补丁** | 复用现成强能力是划算的；但把「有写权限+能跑命令的 Agent」塞进门禁会摧毁发布可信度，且存在提示注入风险 |

**三层自愈优先级（核心架构原则）**：
1. **确定性自愈（无代码变更）** —— 重试/自适应等待/选择器回退链，处理 70–90% 的运行时失败。**这是主层，必须先做**。
2. **定位自愈（改测试资产，非引擎）** —— Healenium 式或 Agent 修复选择器，仅动「被测项目的测试规格」，且必经沙箱校验 + PR/分支。
3. **Agent 语义修复（建 PR，人工把关）** —— 仅当失败属「脚本/契约缺陷」且前两层解决不了时，由 WorkBuddy 类 Agent 在隔离沙箱产出 PR，人审后合入。**当前发布永不因自愈而变绿**。

## 1. 目标与范围界定

### 1.1 要封装成什么
一个独立服务 `verify-service`，对外暴露：
- **被 testhub 远程调用**（按需提交分析/验证任务）；
- **被发布流水线 webhook 触发**（发布完成后自动启动验证，回报门禁结果）。

服务**内部**统一负责：用例编排 → **浏览器调度与执行**（Playwright 真实驱动）→ 断言 → 报告 → （可选）自愈。调用方只拿到结构化结果，不感知浏览器在哪、怎么跑。

### 1.2 本方案聚焦，不重复
- 「服务化四件套」（异步化、鉴权、监控、webhook）详见 `测试加速平台_服务化改造分析.md` §3–§11，**本方案默认已具备**，只补充「浏览器调度」与「自愈」两块增量设计。
- 仍沿 **FastAPI + 任务队列（ARQ）** 栈，不合并进 testhub（定位已在 §服务化分析 中定为独立服务）。

### 1.3 当前代码与目标的 GAP（决定工作量）
| 现状（实测） | 目标 | 缺口性质 |
|---|---|---|
| `executor.py` 仅 `requests` 探活 + 静态文件断言，**零浏览器** | 真实驱动浏览器跑 UI | 能力新建（依赖 `playwright` 已声明，只差执行逻辑） |
| 无浏览器池/并发控制 | 统一调度浏览器、限并发、崩溃隔离 | 新建 `BrowserManager` |
| 失败即整体判 fail/无分类 | 失败分类 → 分级处置（重试/修补/上报） | 新建 `FailureClassifier` + 自愈环 |
| 无 Agent/自动改码 | WorkBuddy 能力按需接入（带外） | 集成（非内生） |

## 2. 失败分类模型（为什么不能一刀切「出错就改代码」）

任何自愈设计的前提是**先把失败分对类**。三类处置路径完全不同：

```
测试执行失败
├─ A. 环境/偶发类 (Environmental / Flaky)
│     典型：超时、元素未挂载、动画进行中、瞬时 5xx、网络抖动
│     处置：确定性重试 + 自适应等待 + 选择器回退 → 不改任何代码 ✅
│
├─ B. 脚本/契约缺陷 (Script / Contract Defect)
│     典型：选择器失效(DOM 改了)、预期值过期、路由被改名、步骤期望错误
│     处置：修补「被测项目的测试规格/资产」(非引擎) → 沙箱校验 → PR → 人工合入 ✅
│
└─ C. 引擎/工具缺陷 (Engine Bug)
      典型：executor 自身抛未捕获异常、DB 错误、逻辑 bug
      处置：上报人工 + 建 issue → 严禁自动改 ✅
```

**关键边界**：
- **永远不动「验证服务自身的引擎代码」**——它是发布门禁，必须稳定、可复现、可审计。
- 即便 B 类，也只改**被测项目的测试资产**（选择器、用例步骤、契约定义），**绝不改引擎**；且改完必经沙箱重跑校验。
- A 类占运行时失败的大头，**且根本不需要改代码**——当前 `executor.py` 连重试都没有，所以第一优先级是补确定性自愈，而不是上 Agent。

## 3. 服务架构（分层 + 模块职责）

```
┌─────────────────────────────────────────────────────────────────┐
│  API Gateway  (FastAPI /api/v1)  —— 鉴权 / 版本化 / 限流 / 路由   │
├─────────────────────────────────────────────────────────────────┤
│  Task Orchestrator (ARQ worker)  —— 异步、task_id、状态机、超时    │
├───────────────────────┬─────────────────────────────────────────┤
│  VERIFY ENGINE        │  HEALER（解耦、异步、带外）              │
│  ├ TestPlanner        │  ├ FailureClassifier                     │
│  ├ BrowserManager ◀───┤  ├ PatchGenerator (WorkBuddy-like Agent │
│  │   (Playwright 池)  │  │     / Healenium / LLM)               │
│  ├ Executor (升级为   │  ├ SandboxValidator (隔离重跑受影响用例) │
│  │   真浏览器驱动)     │  └ PR/分支 + 人工审批闸门               │
│  └ Assertion/Reporter │                                          │
├───────────────────────┴─────────────────────────────────────────┤
│  Storage(Postgres) | ArtifactStore(截图/日志/DOM) | Metrics/Trace │
└─────────────────────────────────────────────────────────────────┘
```

### 3.1 模块职责表

| 模块 | 职责 | 现状 / 改造 |
|---|---|---|
| `APIGateway` | 鉴权、版本化、限流、接收 webhook/任务提交 | 改造 `main.py` 同步端点 → 异步提交（见 §服务化分析 §6） |
| `TaskOrchestrator` | 任务入队、状态机 `pending→running→success/failed`、超时/取消、幂等去重 | 新增（ARQ） |
| `TestPlanner` | 由 cases 生成执行计划（依赖/并行度/顺序） | 部分复用 `case_generator` 产物 |
| `BrowserManager` | **浏览器统一调度**：上下文池、并发上限、临时 profile、崩溃隔离、录屏 | **新建** |
| `Executor`（升级） | 由「静态断言」升级为「Playwright 真驱动 + 保留静态快路径」 | **重写核心**（见 §5） |
| `Assertion/Reporter` | 断言、结果聚合、报告、门禁 JSON | 复用 `html_report`/`reporter` |
| `FailureClassifier` | 捕获失败 → 分类 A/B/C（见 §2） | **新建** |
| `Healer` | 仅对 B 类生成补丁 → 沙箱校验 → 建 PR → 等人工 | **新建（独立进程/容器）** |
| `ArtifactStore` | 截图/DOM/控制台日志/追踪留存，供自愈与复盘 | **新建** |

### 3.2 关键解耦原则
- **Verify Engine 与 Healer 物理隔离**：Healer 只读被测项目副本、只写 PR 分支，**无权访问或修改 Verify Engine 自身代码**。这是门禁可信的生命线。
- **Engine 永远报告真实结果**：即便 Healer 在后台修好了下一版，本次发布的 verdict 仍是原始失败——自愈只服务「未来版本」，不美化「当前版本」。

## 4. 浏览器统一调度设计（BrowserManager）

服务内部统一持有浏览器，调用方与用例都不直接碰 Playwright。

### 4.1 设计要点
- **上下文池（Context Pool）**：预建 N 个隔离 `BrowserContext`（独立 cookie/storage/临时 profile），按任务分配，**任务结束即销毁**，避免状态串扰。
- **并发上限**：全局 `MAX_CONCURRENT_BROWSERS`（如 4），超出排队；防止压垮被测环境与主机。
- **崩溃隔离**：单个 context 崩溃不影响池；`BrowserManager` 监控健康，异常 context 回收重建。
- **可观测**：每次执行留痕——截图（关键步）、`console`/`network` 日志、`trace`（Playwright trace）、录屏（失败用例），统一进 `ArtifactStore`，供自愈与复盘。
- **就绪探测前置**：执行前先探 `health_url`，服务未就绪则指数退避等待（属 A 类自愈），避免无效跑测。

### 4.2 与现有代码关系
- `executor.py` 现有 `_service_check` / `_http_probe` 升级为「Playwright 探活 + 真实交互」；
- 保留其**静态结构断言**作为「快速路径」（无浏览器也能出结构性结论），真实交互走浏览器池——即「静态快、动态准」双轨。

## 5. 运行时错误自愈机制（自愈环）

### 5.1 失败捕获数据结构 `FailureRecord`
```json
{
  "task_id": "v-20260908-abc",
  "case_id": 17,
  "stage": "executing_step",
  "error_type": "NoSuchElement / Timeout / 5xx / EngineError",
  "artifacts": {
    "screenshot": "s3://.../17.png",
    "dom_snapshot": "s3://.../17.html",
    "console_log": "s3://.../17.log",
    "trace": "s3://.../17.zip"
  },
  "failing_step": { "action": "click", "selector": "#submit" }
}
```

### 5.2 自愈状态机
```
run_case
  └─ 失败 → FailureClassifier 分类
       ├─ A(环境/偶发) ──► 确定性重试(指数退避, 自适应 wait-for-stable) ─► 成功则本任务 green
       │                   重试耗尽 → 仍 fail，进 B/C 旁路 + 报告
       ├─ B(脚本/契约) ──► 发布 FailureRecord 到 Healer 队列(异步带外)
       │                   └─ 本次任务仍按真实结果 fail（不自愈变绿）
       └─ C(引擎缺陷)  ──► 上报 + 建 issue，永不自动改
```

### 5.3 三层自愈的实现顺序（务必按此）
1. **L1 确定性自愈（无 Agent、无代码变更）**：重试 + 自适应等待（`wait_for` 稳定态而非固定 sleep）+ 选择器回退链（主选择器失效自动试备用）+ 截图差异容忍。成本低、可靠、必须最先落地。**优先于一切 LLM 方案**。
2. **L2 定位自愈（改测试资产，非引擎）**：引入 Healenium 式定位修复（基于 DOM 结构 ML 匹配自动恢复 locator），或轻量 LLM 产出新 locator；仅写被测项目测试资产，经沙箱重跑校验后入 PR。
3. **L3 Agent 语义修复（建 PR，人工把关）**：仅 B 类且 L1/L2 无解时，由 WorkBuddy 类 Agent 产出 PR（详见 §6）。

## 6. WorkBuddy 集成策略与替代方案

### 6.1 集成定位：**带外自动建 PR 机器人，绝不进实时门禁**
- **不做什么**：不在 `Executor` 执行失败时同步调用 WorkBuddy 改代码、不就地 patch 运行中的服务、不让 Agent 碰 Engine 代码。
- **做什么**：Healer 组件（独立进程/容器）消费 B 类 `FailureRecord` → 调 WorkBuddy（经其 API/CLI，在**隔离沙箱**内）→ 传入**净化的失败上下文** + **被测项目仓库的 fork** → 严格 system prompt（仅允许改 `tests/` 等测试资产路径、禁止改 Engine、禁止执行危险命令）→ 产出 **PR/分支** → CI 在沙箱重跑受影响用例验证 → **人工审批**后合入。
- **门禁不变**：本次发布 verdict 始终是真实结果；WorkBuddy 的修复只影响下一版本。

### 6.2 调用模型（具体）
```
Healer worker
  └─ 拉取 B 类 FailureRecord
     └─ 启动沙箱容器(只读被测 repo 副本 / 写权限仅限新分支)
        └─ 调用 WorkBuddy API：
            system: "你是测试修复助手。仅修改 <allowed_paths> 下的测试资产；
                     不得修改验证引擎；修复后输出 git diff 并创建 PR。"
            user:  FailureRecord(artifacts 已净化) + 复现步骤
        └─ 产出 PR → 触发 CI 沙箱重跑
           ├─ 通过 → 置 pending_review，通知负责人
           └─ 失败 → 丢弃 PR，回退人工
```

### 6.3 必须的安全边界（否则不能上线）
- **提示注入防护**：失败上下文（页面文本、console、报错）可能含恶意指令，入 Agent 前必须**净化/隔离**（视为不可信数据，不进入 system prompt 指令区）。
- **最小权限**：Agent 沙箱**只**能写被测项目的新分支，**不能**访问 Verify Engine 代码、不能访问密钥/DB、命令白名单。
- **VCS 闸门**：所有自动修改必须经 PR + 沙箱 CI + 人工审批；默认**不自动合入**（尤其门禁相关代码）。
- **可回滚**：每次修补带 commit/版本，失败可一键回退。
- **熔断**：Agent 连续 N 次产无效 PR → 停用并告警，转人工。

### 6.4 替代方案对比（不要只会一招）

| 方案 | 改代码？ | 确定性 | 成本 | 适用 | 风险 |
|---|---|---|---|---|---|
| **L1 确定性自愈**（重试/自适应等待/回退链） | 否 | 高 | 低 | A 类（大头） | 极低 ✅主层 |
| **Healenium / 定位自愈库** | 仅 locator | 中高 | 中 | B 类选择器失效 | 低 ✅推荐 L2 |
| **WorkBuddy 类 Agent 建 PR** | 语义修复 | 中（非确定） | 中高 | B 类语义缺陷 | 中（需沙箱+人审）✅L3 |
| **纯人工 + 辅助诊断报告** | 否 | 高 | 人力 | 全部兜底 | 低，但慢 |
| ❌ **同步原地改运行代码** | 是 | 低 | — | 无 | **极高，禁止** |

**选型建议**：L1 必做（先做）；L2 用 Healenium 式定位自愈覆盖大部分 B 类；L3 仅作长尾语义修复的「建 PR」手段，且永不同步进门禁。

## 7. 分阶段执行方案（M0–M3）

| 阶段 | 目标 | 关键交付 | 对应 GAP |
|---|---|---|---|
| **M0 浏览器引擎** | 把 executor 升级为真实 Playwright 驱动 | `BrowserManager` + 重写 `Executor`（双轨：静态快路径 + 浏览器真跑）+ 就绪探测前置 | §1.3 缺口 1/2 |
| **M1 L1 确定性自愈** | 先解决 70–90% 的 A 类失败 | 重试/退避/自适应等待/选择器回退链/`ArtifactStore` 留痕 | §5.3 L1 |
| **M2 失败分类 + L2 定位自愈** | B 类自动恢复 locator | `FailureClassifier` + Healenium 式 locator 自愈（沙箱校验 + PR） | §2 / §5.3 L2 |
| **M3 WorkBuddy 集成（带外）** | 长尾语义修复建 PR | 独立 `Healer` 进程 + WorkBuddy API 调用 + 沙箱 + 人审闸门 + 熔断 | §6 |

> 顺序不可调换：**先有真实浏览器（M0）与确定性自愈（M1），再做 Agent 集成（M3）**。在 L1/L2 没补齐前上 WorkBuddy，会把本可用重试解决的偶发失败误送去改代码，反而引入不稳定。

## 8. 结论与决策建议

1. **关于 Q1（同步改代码自愈）**：**否决「同步原地改运行代码」**。正确做法是「分类 → 分级处置」：A 类靠确定性重试自愈（不改码）；B 类靠带护栏的、异步的、版本化的**测试资产**修补（改的是被测项目规格、非引擎，且经沙箱+PR+人审）；C 类上报人工。**当前发布结果永远反映真实失败，自愈只服务未来版本。**

2. **关于 Q2（集成 WorkBuddy 自动改码）**：**赞成集成，但严格限定为「带外自动建 PR 机器人」**。复用其「读仓库+跑命令+按问题改码」的现成强能力是划算的；但必须物理隔离于门禁：独立进程、沙箱、最小权限、净化上下文防注入、PR+CI+人审、可回滚、熔断。决不让它同步嵌进实时验证流程去改运行中的代码。

3. **架构铁律**：Verify Engine（门禁）保持确定性、可复现、可审计；所有「智能修复」在 Engine 之外闭环，且**永不改变本次发布的 verdict**。

4. **落地优先级**：M0（真浏览器）→ M1（确定性自愈，主层）→ M2（分类+L2 定位自愈）→ M3（WorkBuddy 带外建 PR）。L1 确定性自愈必须先于任何 LLM/Agent 方案。

5. **遗留开放问题**：Healenium 类库与当前 `playwright` 版本的兼容性需 PoC 验证；WorkBuddy 是否提供适合沙箱调用的 API/CLI 入口需确认；Agent 产 PR 的「人审」节奏是否拖慢流水线需与发布策略对齐（门禁阻断 vs 仅告警）。
